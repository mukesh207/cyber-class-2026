# Comprehensive Guide: SSRF, SSTI, and File Upload Vulnerabilities

## The Big Picture: How It All Works Together
In modern web applications, servers often act as intermediaries—fetching external resources, rendering dynamic content, and accepting user files. When an application **implicitly trusts** user input in these specific contexts without proper validation or isolation, it leads to critical vulnerabilities. 

*   **SSRF (Server-Side Request Forgery)** occurs when the server blindly fetches a resource based on user input, turning the server into a weaponized proxy.
*   **SSTI (Server-Side Template Injection)** happens when user input is mistakenly evaluated as native code by a rendering engine, bridging the gap between data and executable logic.
*   **File Upload Vulnerabilities** happen when the server accepts a file but fails to restrict what that file contains or how it gets executed, essentially allowing an attacker to place their own code on the server.

All three share a common root cause: **Mixing untrusted user data with server-side execution/processing logic.**

## 1. Server-Side Request Forgery (SSRF)

### Theory & Mechanics
**Server-Side Request Forgery (SSRF)** is a vulnerability where an attacker forces a server to make HTTP/HTTPS requests on their behalf. 

**Why it works:** Web applications often need to fetch external resources (like a webhook, a profile picture from a URL, or an API). If the application does not validate the URL provided by the user, the attacker can supply an internal IP address (like `127.0.0.1` or `192.168.x.x`). The server, living inside the corporate firewall, has privileges and access that the external attacker does not.

### ASCII Architecture Diagram: Attack Flow
```text
     [External Network]      |           [Internal Network]
                             |
[Attacker]                   |
    |                        |
    | (1) POST /fetch?url=http://127.0.0.1/admin
    v                        |
[Public Web Server] ---------|-------> [Internal Admin Panel] (2) Request sent by Web Server
  (Acts as Proxy)            |                    |
    ^                        |                    | (3) Highly sensitive data returned
    |                        |                    v
    |------------------------|--------- [Public Web Server]
 (4) Data returned to attacker
```

### Real-Time Technical Scenario: Cloud Metadata Exfiltration
**Scenario:** You are testing an application hosted on AWS that allows users to export data via a webhook URL. 
**The Attack:** You provide the AWS Metadata IP: `http://169.254.169.254/latest/meta-data/iam/security-credentials/`.
**The Result:** The web server fetches its own AWS IAM keys and sends them back to you. You now have full cloud infrastructure access.

### Hands-On Practice: Spotting & Exploiting SSRF
**Observation:** You see a parameter like `?url=`, `?dest=`, `?webhook=`, or `?path=`.
**Hypothesis:** The server might be fetching this resource directly.
**Test:** Provide a burp collaborator payload or webhook.site URL.
**Result:** You receive an HTTP request from the target server's IP.
**Conclusion:** The endpoint is vulnerable to SSRF. 

**Practical HTTP Request (Bypassing basic filters):**
Sometimes developers block `127.0.0.1`. You can bypass this using:
*   Decimal IP: `http://2130706433/`
*   IPv6: `http://[::1]/`
*   DNS resolution: `http://localtest.me` (resolves to 127.0.0.1)

## 2. Server-Side Template Injection (SSTI)

### Theory & Mechanics
**Server-Side Template Injection (SSTI)** occurs when an attacker is able to use native template syntax to inject a malicious payload into a template, which is then executed on the server.

**Why it works:** Web frameworks use **Template Engines** (like Jinja2 for Python, Twig for PHP, or FreeMarker for Java) to separate HTML design from backend logic. They use placeholders like `{{ name }}`. If a developer directly concatenates user input into the template string *before* rendering, rather than passing it as a safe variable, the engine will parse the attacker's input as code.

### ASCII Architecture Diagram: Request Flow
```text
[User Input: {{ 7 * 7 }}] 
          |
          v
[Web App Backend] 
  (Code: template_string = "Hello " + user_input)
          |
          v
[Template Engine (e.g., Jinja2)]
  (Evaluates {{ 7 * 7 }} native logic)
          |
          v
[Rendered Output: "Hello 49"] --> (Sent back to Attacker)
```

### Real-Time Technical Scenario: Remote Code Execution via Jinja2
**Scenario:** A customized 404 page reflects the URL you tried to visit. 
**The Attack:** You visit `/page/{{config.__class__.__init__.__globals__['os'].popen('id').read()}}`.
**The Result:** The Python Jinja2 engine traverses the object hierarchy to find the `os` module, executes the `id` command, and returns the output (e.g., `uid=33(www-data)`). This is full **Remote Code Execution (RCE)**.

### Hands-On Practice: SSTI Identification
**Observation:** User input is heavily reflected on the page without HTML encoding, particularly in customized emails or error pages.
**Test Strategy:** Inject math operations to see if they are evaluated.
| Template Engine | Payload | Expected Output |
| :--- | :--- | :--- |
| Smarty (PHP) | `{*7*7}` | `49` |
| Jinja2 / Twig | `{{7*7}}` | `49` |
| FreeMarker (Java)| `${7*7}` | `49` |

## 3. File Upload Vulnerabilities

### Theory & Mechanics
A **File Upload Vulnerability** happens when a web server allows users to upload files to its filesystem without sufficiently validating the file's name, type, contents, or size. 

**Why it works:** If a server expects an image (`profile.png`) but an attacker uploads a script (`shell.php`), and the server stores it in a publicly accessible directory (`/uploads/shell.php`), the attacker can navigate to that file in their browser. The web server (like Apache or Nginx) will see the `.php` extension and dutifully execute the malicious code.

### ASCII Architecture Diagram: Execution Flow
```text
1. [Attacker] --(Uploads: 'shell.php')--> [Web Server (Validation logic)]
                                                  |
                                       (Fails to validate extension properly)
                                                  |
                                                  v
                                       [Filesystem: /var/www/html/uploads/shell.php]

2. [Attacker] --(GET /uploads/shell.php)--> [Web Server (Apache/Nginx)]
                                                  |
                                       (Sees .php, passes to PHP handler)
                                                  |
                                                  v
                                       [PHP Engine Executes Attacker's Script]
```

### Real-Time Technical Scenario: Bypassing Image Filters
**Scenario:** A forum allows profile picture uploads but checks if the file ends in `.jpg`.
**The Attack:** You create a PHP web shell. You rename it to `shell.php.jpg`. If the backend only checks if the string *ends with* `.jpg` but Apache is configured to execute any file *containing* `.php`, the script will run. 
Alternatively, you use a **Null Byte Injection** (`shell.php%00.jpg`), tricking the application's C-based backend into terminating the string early (saving it as `shell.php`), while bypassing the high-level validation regex.

### Hands-On Practice: Bypassing File Upload Restrictions
When testing an authorized file upload feature, use this workflow:

1.  **Test Client-Side Filters:** Intercept the upload in Burp Suite. Client-side JavaScript restrictions are useless once the request is intercepted.
2.  **Test Extension Blacklisting:** If `.php` is blocked, try alternative extensions: `.php3, .php4, .php5, .phtml, .phar`.
3.  **Test Content-Type Spoofing:** Change the `Content-Type: application/x-php` header in the HTTP request to `Content-Type: image/jpeg`.
4.  **Test Magic Bytes:** Some servers read the first few bytes of a file to determine its type. Add `GIF89a;` at the very top of your PHP script to trick the server into thinking it's a GIF image.
