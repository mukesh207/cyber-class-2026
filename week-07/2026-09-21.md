## 🌍 The Big Picture: How YARA Works

**YARA** is often referred to as the "pattern-matching Swiss army knife" for malware researchers. Instead of relying on traditional hash-based detection (which fails the moment a single byte of a file changes), YARA allows analysts to create custom **rules** based on specific text or binary patterns found within a file or running process.

**WHY it works:** YARA scans the raw bytes of a file (or memory space) and evaluates those bytes against boolean expressions defined by the analyst. If the conditions are met (e.g., String A AND String B are present), it "matches" and identifies the file. This makes it incredibly powerful for grouping related malware families that share code structures, embedded URLs, or specific hex strings, even if they have been slightly modified or recompiled.

```text
+-------------------+        +-------------------+        +-------------------+
|   Suspect Files   |        |    YARA Engine    |        |  Match Results    |
| - malicious.exe   |  --->  | - Reads Rule      |  --->  | - Rule 'Banker'   |
| - document.pdf    |        | - Scans Bytes     |        |   matched on      |
| - memory_dump.bin |        | - Evaluates Logic |        |   malicious.exe   |
+-------------------+        +-------------------+        +-------------------+
                                      ^
                                      |
                             +-------------------+
                             |   YARA Rule (.yar)|
                             | - Strings defined |
                             | - Conditions set  |
                             +-------------------+
```

## 🧠 Theory: Anatomy of a YARA Rule

A YARA rule is essentially a boolean statement with three main sections:
1. **Meta (Optional but Recommended):** Metadata about the rule (author, description, date, hashes). This does not affect detection.
2. **Strings (Optional but Common):** The specific patterns to search for. These can be ASCII text, hex sequences, or regular expressions.
3. **Condition (Mandatory):** The logic that dictates *when* the rule should trigger.

### Example: Basic Rule Structure

```yara
rule Suspicious_Banker {
    meta:
        description = "Detects silent banker trojan strings"
        author = "Mukesh"
        threat_level = "High"

    strings:
        $hex_pattern = { 6A 40 68 00 30 00 00 6A 14 8D 91 } // Raw hex bytes
        $url = "http://malicious-bank-login.com" ascii wide // Text string
        $sus_func = "StealCredentials" nocase             // Case-insensitive

    condition:
        $hex_pattern or ($url and $sus_func)
}
```

### String Modifiers Comparison

| Modifier | Purpose / WHY use it? |
| :--- | :--- |
| `nocase` | Ignores capitalization. Useful when attackers change case to evade simple exact-match signatures (e.g., `cmd.exe` vs `CmD.eXe`). |
| `wide` | Matches 2-byte (UTF-16) characters often used in Windows/PE files. "A" becomes `41 00` instead of `41`. |
| `ascii` | Matches 1-byte characters. Often combined with `wide` (`ascii wide`) to search for a string in both formats simultaneously. |
| `fullword` | Ensures the match is bordered by non-alphanumeric characters. Prevents false positives (e.g., searching for "cmd" won't match "cmdlet"). |

## 🛠️ Hands-On Practice

*Assume all actions are performed in a controlled, authorized sandbox environment.*

### Real-Time Technical Scenario
**Scenario:** A SOC alert fired for a suspicious executable dropped in `C:\Users\Public\`. We suspect it is a known keylogger. We need to write a YARA rule to verify this and then use the YARA CLI to scan the directory.

**Hypothesis:** The executable contains a specific hardcoded C2 IP (`192.168.100.55`) and the string `StartKeyLogger`.
**Test:** We create a YARA rule and run it against the suspect file.

**Step 1: Write the Rule (`keylogger.yar`)**
```yara
rule Custom_Keylogger {
    meta:
        description = "Identifies suspected keylogger based on C2 and function name"
    strings:
        $c2 = "192.168.100.55" wide ascii
        $func = "StartKeyLogger" nocase
    condition:
        all of them
}
```

**Step 2: Execute YARA via CLI**
The basic syntax is `yara [options] [rule_file] [target_file_or_dir]`.

```bash
# Command:
yara -m keylogger.yar /home/st4rk/suspect_files/

# Observation / Output:
Custom_Keylogger [description="Identifies suspected keylogger based on C2 and function name"] /home/st4rk/suspect_files/dropped_file.exe
```

**Result & Conclusion:** The rule matched `dropped_file.exe`, verifying our hypothesis. The `-m` flag printed the metadata, confirming why the rule was created.

## 🔍 Advanced Concepts (Brief)

- **File Size Conditions:** You can restrict rules to certain file sizes to improve performance. `condition: filesize < 500KB and $a`
- **Entry Point Matching:** For PE (Windows) or ELF (Linux) files, you can check if a pattern occurs at the exact entry point of the program.
- **Modules:** YARA can import modules (like `pe`, `elf`, `hash`, `math`) to perform deep structural analysis of binary headers rather than just raw byte searching.
