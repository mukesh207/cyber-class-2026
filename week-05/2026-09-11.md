# Cybersecurity Notes: Windows Fundamentals, Forensics & Active Directory

## The Big Picture: How It All Works Together
In an enterprise environment, Windows is the most common operating system. An organization doesn't just have random computers; they are managed centrally using **Active Directory (AD)**. Employees interact with the network using either **Thin Clients** (web browsers accessing remote servers) or **Thick Clients** (applications installed directly on the computer). When an attacker breaches the network or a SOC analyst investigates an incident, the evidence is left behind in **Windows Forensics Artifacts** like logs, registry entries, and cache files. Understanding this ecosystem is the foundation of both attacking and defending enterprise networks.

---

## 1. Client Architecture: Thick Client vs. Thin Client

When assessing or defending applications, you need to know where the processing happens and where the data is stored.

### Thick Client
A **Thick Client** (or "Fat Client") is a full-featured software application installed locally on the user's computer. It performs most of its data processing locally and relies less on the server for basic operations.
*   **Security Context (Why it matters):** Because the app runs locally, it interacts deeply with the local OS. It stores sensitive data in local files, memory, and the **Windows Registry**. Attackers can reverse-engineer the binary, dump memory to steal credentials, or tamper with local configuration files.
*   **Example:** Microsoft Outlook desktop app, Slack desktop client, custom enterprise ERP apps.

### Thin Client
A **Thin Client** is typically a web browser or a lightweight application that relies heavily on a central server for processing and data storage.
*   **Security Context (Why it matters):** The local machine stores very little. The attack surface shifts to the network (intercepting traffic) or the server itself (SQL injection, server-side exploits). On the client side, attackers focus on browser artifacts like cookies or local storage.
*   **Example:** Outlook on the Web (OWA), Google Workspace, Salesforce web app.

### Comparison Table
| Feature | Thick Client | Thin Client |
| :--- | :--- | :--- |
| **Processing Power** | High reliance on local CPU/RAM | Low reliance locally, depends on server |
| **Data Storage** | Stores cache, config, logs locally | Stores minimal data (cookies, DOM) locally |
| **Attack Surface** | Local binary tampering, memory dumping, registry hijacking | Web vulnerabilities (XSS, CSRF), API abuse |
| **Forensic Evidence** | App-specific logs, Registry keys, large cache files | Browser history, cache, downloaded files |

## 2. Active Directory (AD) Concepts & Global Usage

**Active Directory** is a directory service developed by Microsoft. Think of it as the central phonebook and security guard for the entire enterprise. It manages all users, computers, and permissions.

### Core Components
*   **Domain:** A logical group of computers and users that share a common directory database (e.g., `corp.company.com`).
*   **Domain Controller (DC):** The boss. The server that runs Active Directory, authenticates users, and enforces security policies. If an attacker compromises the DC, they own the entire network.
*   **Organizational Unit (OU):** Folders within the domain used to organize objects (e.g., placing all HR computers in an HR OU).
*   **Group Policy Object (GPO):** A set of rules applied to an OU or Domain. For example, a GPO can force all workstations to disable USB drives.
*   **Kerberos & NTLM:** The core authentication protocols. Kerberos uses "tickets" to grant access, while NTLM uses challenge-response mechanisms.

### How Organizations Use AD Across Countries
When a massive organization operates globally, having just one Domain Controller in the US would mean an employee in the UK would experience massive lag when logging in, as authentication traffic crosses the ocean. 

To solve this, AD uses **Sites and Subnets**:
*   **AD Sites:** A Site represents a physical location (e.g., "New York Office", "London Office"). 
*   **Subnets:** IP ranges are mapped to these Sites. If an employee's computer gets an IP in the `10.2.x.x` range, AD knows they are in London.
*   **Replication:** The Domain Controllers in different countries sync (replicate) their databases with each other behind the scenes. 
*   **The Workflow:** When the UK employee logs in, their computer checks DNS, finds the nearest DC based on their Site, and authenticates locally. If the UK DC goes down, it will gracefully fall back to the US DC.

## 3. Windows Forensic Techniques (SOC & Incident Response)

When an attacker moves through a Windows system, they leave footprints. Forensics is about finding and interpreting those footprints.

### A. Windows Event Logs (.evtx)
Windows records significant system, security, and application events.
*   **Location:** `C:\Windows\System32\winevt\Logs\`
*   **Key Logs for SOC:**
    *   **Security:** Logon attempts, privilege use.
    *   **System:** Service starts/stops, system errors.
*   **Crucial Event IDs to Memorize:**
    *   **4624:** Successful Logon
    *   **4625:** Failed Logon
    *   **4688:** Process Creation (Crucial for seeing what commands an attacker ran)
    *   **7045:** New Service Installed (Attackers often install services to maintain persistence)

**Practical Command (PowerShell):**
```powershell
# Search for failed logons in the last 24 hours
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625; StartTime=(Get-Date).AddDays(-1)}
```

### B. Prefetch Files (.pf)
Windows tracks which applications are launched to make them load faster next time.
*   **Location:** `C:\Windows\Prefetch\`
*   **Forensic Value:** Proves that an executable actually **ran** on the system, even if the attacker deleted the executable afterward. It shows the run count and the last execution time.

### C. Registry Evidence
The registry is the central configuration database.
*   **NTUSER.DAT:** A hidden file in every user's profile (`C:\Users\<username>\NTUSER.DAT`). It contains registry settings specific to that user. Forensics can pull this to see what files the user recently opened (RecentDocs) or what programs they executed (UserAssist).
*   **Autoruns (Persistence):** Attackers add keys here so their malware starts when the computer boots.
    *   *Path:* `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run`

### D. Amcache and Shimcache
*   **Shimcache (Application Compatibility Cache):** Tracks executables that have interacted with the system to ensure compatibility. It records the file path, last modified time, and whether it was executed.
*   **Amcache:** Similar to Shimcache but stores the SHA1 hash of the executable.
*   **Why we care:** Even if an attacker renames a malicious file, the hash in the Amcache can identify it.

## 4. Real-Time Technical Scenarios

### Scenario 1 (SOC Analyst) - Investigating a Brute Force Attack
*   **Observation:** The SIEM alerts on 500 instances of Event ID **4625** (Failed Logon) for the user "Admin" within 2 minutes, originating from IP 192.168.1.50.
*   **Hypothesis:** An attacker is attempting to brute-force the Admin account.
*   **Test/Investigation:** Look for an eventual Event ID **4624** (Successful Logon) from that same IP for the "Admin" account immediately following the failures.
*   **Conclusion:** If 4624 is found, the brute force succeeded. The SOC must isolate the host, reset the password, and investigate what processes were created (Event ID **4688**) after the successful logon.

### Scenario 2 (Penetration Tester) - Exploiting a Thick Client
*   **Fact:** The target organization uses a custom internal HR Thick Client application.
*   **Observation:** By running the application through a local proxy (like Burp Suite) and monitoring file activity using Sysinternals **Process Monitor (ProcMon)**, the pentester notices the application saves database connection strings (with hardcoded credentials) in a local cache file.
*   **Conclusion:** The Thick Client relies too heavily on client-side security. The pentester extracts the credentials from the local cache and uses them to connect directly to the backend database, bypassing the application's login screen entirely.

### Scenario 3 (SOC/Pentester) - Global AD Trust Abuse
*   **Observation:** An attacker compromises a weak, poorly secured Domain Controller in a branch office in Country A. 
*   **Action:** Because all domains in the forest trust each other by default (Transitive Trust), the attacker creates a "Golden Ticket" (forged Kerberos ticket) using the compromised DC's keys.
*   **Conclusion:** The attacker uses the forged ticket to access highly sensitive financial servers located in the headquarters in Country B. This highlights why securing *all* AD replication sites is critical, not just the main headquarters.
