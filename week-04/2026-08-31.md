## 1. The Big Picture: Layered Defense Architecture

In modern enterprise environments, no single security device can withstand every vector of attack. Perimeter defenses must allow external users to access public web services, yet that very access exposes organizations to exploitation, reconnaissance, and denial of service.

To solve this dilemma, network architects implement **Defense-in-Depth**—a strategy that layers complementary defensive mechanisms so that if an attacker bypasses one control, subsequent layers detect, delay, or neutralize the threat.

### Enterprise Defense-in-Depth Architecture

```text
                                [ The Wild Internet ]
                             (Untrusted Public Traffic)
                                         |
                                         v
                         +-------------------------------+

                         |  (BGP Routing, Anti-DDoS,     |

+=================================================================================+
|                      PERIMETER NETWORK FIREWALL (Layer 3 / 4)                   |

+=================================================================================+
                   |                                             |
```

### How the Layers Complement Each Other
1. **Gateway Router:** Manages border gateway protocol (**BGP**) routes and sheds volumetric DDoS attacks before they saturate internal links.
2. **Network Firewall (L3/L4):** Enforces network boundaries. It permits web traffic on ports 80/443 while dropping traffic destined for internal ports like 22 (SSH), 445 (SMB), or 3389 (RDP).
3. **NIPS / NIDS:** Inspects packet streams for malicious signatures (e.g., known exploit shellcode, port scans).
4. **Load Balancer (HA):** Distributes incoming connections across redundant servers and offloads cryptographic TLS handshakes.
5. **WAF (L7):** Inspects the decrypted HTTP payload for application-specific exploits (SQLi, XSS, Path Traversal) that network firewalls cannot parse.
6. **Web Servers (DMZ):** Process business logic and return web content fortified with **HTTP Security Headers** to safeguard the client's browser.
7. **Internal Firewall:** Prevents a compromised web server from pivoting freely into core databases or management networks.

## 2. Core Security Appliances: Mechanics & Comparison

Network security appliances operate at different layers of the **OSI Model**. Understanding their operational layer explains both their capabilities and their blind spots.

```text
OSI Layer           Security Appliance               Inspection Focus
--------------------------------------------------------------------------------
Layer 7 (App)       Web Application Firewall (WAF)   HTTP verbs, parameters, payloads, cookies
Layers 4-7          Intrusion Prevention (IPS)       Transport payloads, protocol anomalies, signatures
Layers 3-4          Stateful Network Firewall        IP addresses, TCP/UDP ports, connection state
Layer 2 (Data Link) Switches & VLANs                 MAC addresses, 802.1Q tags, frame isolation
```

### Network Firewalls (Layer 3 / 4)
*   **Mechanism:** A **Stateful Packet Inspection (SPI)** firewall monitors the state of active TCP sessions. It tracks the three-way handshake (`SYN` -> `SYN-ACK` -> `ACK`) in a state table. Once established, return packets matching the existing connection are permitted automatically.
*   **Limitation:** It is application-blind. If an attacker submits a malicious SQL injection payload like `' OR 1=1 --` inside an HTTP POST request to port 443, the firewall sees only legitimate TCP packets addressed to an authorized port and allows them through.

### Intrusion Detection (IDS) vs. Intrusion Prevention (IPS)
Both systems analyze network traffic against a database of known threat signatures and behavioral baselines. The critical difference lies in **how they sit on the network wire**.

```text
       PASSIVE / OUT-OF-BAND (NIDS)                      ACTIVE / IN-LINE (NIPS)
       
      Incoming Packet Stream                            Incoming Packet Stream
               |                                                 |
               v                                                 v
    +--------------------+                            +--------------------+
    |    Network Tap /   |                            |                    |
    |     SPAN Port      |                            |     In-Line IPS    |
    +--------------------+                            |                    |
       |              |                               +--------------------+
       | Copy         | Original Traffic                         |
       v              v                                          | Allowed Packets
    [ NIDS ]    [ Web Server ]                                   v
       |                                                  [ Web Server ]
       v
 (Generates Alert to SIEM;
  Cannot drop live packet)                             (Drops malicious packet;
                                                        Terminates connection via TCP RST)
```

*   **NIDS (Passive / Out-of-Band):**
    *   Traffic is mirrored to the sensor using a physical **TAP** (Test Access Point) or a switch **SPAN** (Switched Port Analyzer) port.
    *   **Advantage:** Zero latency introduced into production traffic. If the sensor fails, user traffic is completely unaffected.
    *   **Disadvantage:** Detection occurs *after* the packet has already reached the destination. It can alert administrators, but it cannot prevent exploitation in real time.
*   **NIPS (Active / In-Line):**
    *   All production traffic must physically pass through the appliance.
    *   **Advantage:** Can drop malicious packets mid-stream or send a `TCP RST` (Reset) to terminate rogue connections immediately.
    *   **Disadvantage:** Introduces a small amount of latency. If improperly configured or overwhelmed, it can become a network bottleneck, drop legitimate traffic (False Positive impact), or act as a single point of failure.

### Web Application Firewall (WAF - Layer 7)
*   **Mechanism:** A **WAF** operates as a reverse proxy sitting in front of web applications. It terminates or inspects decrypted HTTP/HTTPS requests.
*   **Inspection Logic:** It parses HTTP request components:
    *   Request URI and query strings (e.g., `?id=1 UNION SELECT...`)
    *   HTTP headers (e.g., malicious `User-Agent`, spoofed `Host` headers)
    *   Request body payloads (e.g., JSON, XML, multipart form data)
    *   Cookies and session identifiers
*   **Rule Sets:** Commonly powered by rules like the **OWASP ModSecurity Core Rule Set (CRS)**, which match regular expressions and score anomalies across common application vulnerabilities.

### Defensive Appliances Comparison

| Feature | Network Firewall (L3/L4) | IDS (Passive) | IPS (Active) | WAF (Layer 7) |
| :--- | :--- | :--- | :--- | :--- |
| **Primary Layer** | OSI Layer 3 (Network) & 4 (Transport) | Layers 3, 4, and 7 | Layers 3, 4, and 7 | OSI Layer 7 (Application) |
| **Placement** | Perimeter / Zone Boundaries (In-line) | Out-of-band (SPAN/TAP) | In-line on wire | In front of Web Servers (Reverse Proxy) |
| **Action on Threat** | Drops packets by rule | Generates alert / log | Drops packet / resets session | Blocks HTTP request (403 Forbidden) |
| **Inspection Depth** | IP headers, TCP/UDP ports, TCP flags | Full packet stream (signatures) | Full packet stream (signatures) | HTTP methods, headers, URLs, payloads |
| **Encrypted HTTPS** | Cannot decrypt; sees port 443 stream | Blind unless TLS terminated upstream | Blind unless TLS terminated upstream | Terminates or inspects decrypted TLS |
| **Primary Threat Focus**| Port scans, unauthorized services, IP spoofing | Known exploits, command & control beacons | Active exploits, worm propagation, DoS | SQLi, XSS, CSRF, RFI/LFI, SSRF |

## 3. High Availability (HA) & Load Balancing

High Availability ensures that service delivery continues uninterrupted despite hardware failure, software crashes, or network interruptions, fulfilling the **Availability** pillar of the CIA Triad.

### Single Point of Failure (SPOF)
A **Single Point of Failure (SPOF)** is any individual component whose failure brings down the entire system. Redundancy eliminates SPOFs by clustering critical devices (firewalls, routers, load balancers, web servers).

### Clustering Architectures: Active/Passive vs. Active/Active

```text
            ACTIVE / PASSIVE CLUSTER                             ACTIVE / ACTIVE CLUSTER
            
             Virtual IP (VIP): 203.0.113.10                       Virtual IP (VIP): 203.0.113.10
                     |                                                    |
         +-----------+-----------+                            +-----------+-----------+
         |                       |                            |                       |
         v                       v                            v                       v
+-----------------+     +-----------------+          +-----------------+     +-----------------+
| Primary Node    |     | Secondary Node  |          | Node 01         |     | Node 02         |
| (Active)        |     | (Standby/Idle)  |          | (Active - 50%)  |     | (Active - 50%)  |
| Handles 100%    |     | Handles 0%      |          | Handles traffic |     | Handles traffic |
+-----------------+     +-----------------+          +-----------------+     +-----------------+
         ^                       ^                            ^                       ^
         |      Heartbeat        |                            |      Heartbeat        |
         +=======================+                            +=======================+
           (State Sync / Ping)                                  (State Sync / Session)
```

#### 1. Active/Passive (Failover Mode)
*   **How it works:** The primary device handles all incoming production traffic under a shared **Virtual IP (VIP)**. The secondary node remains idle in standby mode. Both devices communicate continuously over a dedicated **Heartbeat Cable**.
*   **Failover Mechanism:** If the primary node stops responding (heartbeat interrupted), the secondary node assumes ownership of the VIP using **Gratuitous ARP (GARP)** and begins processing traffic immediately.
*   **Pros/Cons:** Simple to maintain and eliminates session desynchronization; however, half the expensive hardware sits idle.

#### 2. Active/Active (Load-Sharing Mode)
*   **How it works:** All nodes in the cluster process traffic concurrently. Incoming traffic is distributed across all active appliances using a load-balancing algorithm.
*   **State Synchronization:** Stateful appliances (like firewalls) must continuously synchronize their active session tables across the heartbeat link so that if Node 01 dies, Node 02 can seamlessly handle existing TCP sessions without disconnecting users.
*   **Pros/Cons:** Maximum hardware utilization and higher total throughput; however, configuration complexity is high, and if one node fails, the surviving node must handle the entire load without degrading.

### HA Architecture Comparison

| Metric | Active / Passive | Active / Active |
| :--- | :--- | :--- |
| **Resource Utilization** | 50% (Secondary node sits idle) | 100% (All nodes actively work) |
| **Failover Performance** | Brief delay while secondary promotes and broadcasts GARP | Instantaneous for new connections; existing sessions rely on sync |
| **State Table Overhead** | One-way state replication (Primary -> Secondary) | Bidirectional continuous synchronization |
| **Capacity Planning** | Total cluster capacity = Single node capacity | Must run below 50% capacity per node to survive node failure |
| **Operational Complexity**| Low | High |

## 4. Deception Systems: Honeypots & Threat Intelligence

A **Honeypot** is an intentionally vulnerable or exposed decoy system deployed on a network with no legitimate business purpose. It acts as an early warning sensor and intelligence-gathering trap.

```text
                             [ Attacker Reconnaissance ]
                                         |
                                         v
                                [ Enterprise Network ]
                                         |
                     +-------------------+-------------------+
                     |                                       |
                     v                                       v
          +---------------------+                 +---------------------+
          | Real Production Web |                 |   Honeypot Decoy    |
          | - Legitimate users  |                 | - ZERO valid users  |
          | - Heavy noise/logs  |                 | - ANY interaction   |
          | - Strict filtering  |                 |   is an attack!     |
          +---------------------+                 +---------------------+
                                                             |
                                                             v
                                                  +---------------------+
                                                  | High-Fidelity Alert |
                                                  | - Instant SOC alarm |
                                                  | - Captures tooling, |
                                                  |   payloads, & TTPs  |
                                                  +---------------------+
```

### Why Honeypots are Defensively Powerful
1. **Zero False Positives:** Because legitimate employees and customers have no reason to access a honeypot's IP address or hostname, **every single connection attempt is inherently suspicious**.
2. **Attacker Slowdown:** Diverts attacker attention and resources away from genuine high-value production databases and servers.
3. **Intelligence Gathering:** Captures zero-day exploits, novel malware binaries, and adversary **Tactics, Techniques, and Procedures (TTPs)** before they are deployed against real assets.

### Interaction Levels: Low vs. High Interaction

```text
Low-Interaction Honeypot                          High-Interaction Honeypot
(e.g., Cowrie, Dionaea)                           (Real OS in Isolated Sandbox)
+-----------------------------------+             +-----------------------------------+
| Emulated Services                 |             | Actual Linux / Windows OS         |
| - Fake SSH banner                 |             | - Real Bash shell                 |
| - Accepts passwords, logs inputs  |             | - Real file system & kernel       |
| - Limited fake commands (ls, pwd) |             | - Deep telemetry & session record |
+-----------------------------------+             +-----------------------------------+
- Safe, lightweight                               - High fidelity, captures zero-days
- Easily spotted by skilled attackers             - High risk: must prevent pivoting!
```

### How Attackers Identify and Evade Honeypots
Experienced penetration testers and attackers actively scan for indicators that a machine is a decoy:

*   **Unrealistic Isolation:** A real production server connects to active databases, domain controllers, DNS, and logging infrastructure. A honeypot sitting completely isolated with no outbound network traffic or reachable internal neighbors is suspicious.
*   **"Too Easy" Exploitation:** If a system leaves default credentials (`admin:admin`, `root:toor`) enabled on an externally exposed interface, or presents a trivial 10-year-old remote code execution vulnerability without any patching, it is often a trap.
*   **Emulated Shell Artifacts:** In low-interaction honeypots, standard Linux utilities fail or produce canned responses. Commands like `cat /proc/cpuinfo`, `uname -a`, or piping commands (`ps aux | grep root`) may fail or output static mock data.
*   **TCP/IP Fingerprinting Inconsistencies:** Tools like `nmap` analyze TCP window sizes, initial sequence number (ISN) predictability, and IP identification (IPID) behavior. A mismatch between the reported web server banner (e.g., IIS on Windows) and the underlying network stack (e.g., a Python script running on Linux) exposes the deception.

## 5. Web Application Protocol: HTTP/HTTPS Mechanics

Web applications communicate over **HTTP (Hypertext Transfer Protocol)**, a stateless, client-server protocol operating at Layer 7. Because HTTP transactions are independent and stateless, modern web applications rely on headers, cookies, and tokens to preserve session context and enforce security boundaries.

### The Complete HTTP Request / Response Lifecycle

```text
   [ Client Browser ]                                            [ Web Application Server ]
           |                                                                 |
           | ------------------ 1. HTTP Request (Plaintext) ---------------> |
           |      GET /api/user/profile HTTP/1.1                             |
           |      Host: portal.target-lab.local                              |
           |      User-Agent: Mozilla/5.0 (X11; Linux x86_64) ...            |
           |      Accept: text/html,application/xhtml+xml                    |
           |      Cookie: session_token=ab7f9c2d81e4; user_id=402            |
           |      Connection: keep-alive                                     |
           |                                                                 |
           |                                                      [ 2. Server Validates ]
           |                                                      - Checks session token
           |                                                      - Queries database
           |                                                      - Prepares payload
           |                                                      - Appends Security Headers
           |                                                                 |
           | <----------------- 3. HTTP Response (Plaintext) <-------------- |
           |      HTTP/1.1 200 OK                                            |
           |      Date: Mon, 31 Aug 2026 10:00:00 GMT                        |
           |      Server: Apache/2.4.52 (Ubuntu)                             |
           |      Content-Type: text/html; charset=UTF-8                     |
           |      Content-Length: 1420                                       |
           |                                                                 |
           |      --- CRITICAL SECURITY HEADERS ENFORCED ---                 |
           |      Strict-Transport-Security: max-age=31536000; includeSub... |
           |      Content-Security-Policy: default-src 'self'; script-src...|
           |      X-Frame-Options: DENY                                      |
           |      X-Content-Type-Options: nosniff                            |
           |      Set-Cookie: session_token=...; Secure; HttpOnly; SameSite |
           |                                                                 |
           |      [ HTML / Application Data Body ]                           |
```

### HTTP Request Methods (Verbs)

| Method | Idempotent? | Safe? | Purpose | Security Considerations |
| :--- | :---: | :---: | :--- | :--- |
| **GET** | Yes | Yes | Retrieve resource without altering server state | Sensitive data must **never** be placed in query strings (logged in proxy/browser history). |
| **POST** | No | No | Submit data to create or process a resource | Requires Anti-CSRF tokens to prevent forged submissions. |
| **PUT** | Yes | No | Replace or create target resource completely | If misconfigured/unauthenticated, allows arbitrary file upload / web shell placement. |
| **DELETE** | Yes | No | Remove specified resource from server | Must enforce strict role-based access control (RBAC). |
| **HEAD** | Yes | Yes | Identical to GET, but returns headers only | Used for fast recon and header auditing without downloading the page body. |
| **OPTIONS**| Yes | Yes | Inquires about supported communication options | Reveals allowed verbs (CORS enumeration); can reveal insecure methods like `PUT`/`DELETE`. |

### HTTP Status Code Families & Security Implications

```text
Status Range     Class               Security Significance
----------------------------------------------------------------------------------------------------
1xx              Informational       Protocol handshakes (e.g., 101 Switching Protocols to WebSocket)
2xx              Success             Request succeeded (200 OK, 201 Created, 204 No Content)
3xx              Redirection         URL changes (301 Permanent, 302 Found). Watch for Open Redirects!
4xx              Client Error        Invalid input or unauthorized access:
                                     - 401 Unauthorized: Missing or invalid credentials
                                     - 403 Forbidden: Authenticated, but lacking permission / WAF blocked
                                     - 404 Not Found: Resource absent (reveals directory enum results)
5xx              Server Error        Server-side failure (500 Internal Error, 502 Bad Gateway).
                                     - Critical: May leak verbose database stack traces to attackers!
```

## 6. HTTP Security Headers: Client-Side Defense

While the WAF protects the server from malicious requests, **HTTP Security Headers** instruct the client's web browser on how to securely render content, execute scripts, and isolate sessions.

```text
              ATTACK VECTOR                                  DEFENSIVE HEADER
              
    +-------------------------------+               +-------------------------------+
    | Cross-Site Scripting (XSS)    | ------------> | Content-Security-Policy (CSP) |
    +-------------------------------+               +-------------------------------+
    | SSL Stripping (HTTP Downgrade)| ------------> | Strict-Transport-Security     |
    +-------------------------------+               +-------------------------------+
    | Clickjacking (Iframe Overlay) | ------------> | X-Frame-Options               |
    +-------------------------------+               +-------------------------------+
    | MIME-Type Sniffing Exploit    | ------------> | X-Content-Type-Options        |
    +-------------------------------+               +-------------------------------+
    | Session Cookie Theft via XSS  | ------------> | Set-Cookie: HttpOnly; Secure  |
    +-------------------------------+               +-------------------------------+
```

### Deep Dive: How Security Headers Function

#### 1. Content-Security-Policy (CSP)
*   **Why it works:** Cross-Site Scripting (XSS) succeeds when an attacker injects malicious JavaScript into an application and the victim's browser blindly executes it. CSP restricts the domains and sources from which scripts, styles, and images can be loaded or executed.
*   **Example:**
    ```http
    Content-Security-Policy: default-src 'self'; script-src 'self' https://trustedscripts.cdn.com; object-src 'none';
    ```
    Even if an attacker injects `<script src="http://evil-attacker.com/steal.js"></script>`, the browser refuses to load the script because the source domain is not allowlisted.

#### 2. Strict-Transport-Security (HSTS)
*   **Why it works:** Prevents **SSL Stripping** (Man-in-the-Middle downgrade attacks where an attacker intercepts an initial unencrypted HTTP connection before redirecting to HTTPS).
*   **Example:**
    ```http
    Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
    ```
    Instructs the browser to strictly communicate via HTTPS for the next year (`31536000` seconds). Any attempt to access `http://` is automatically upgraded client-side to `https://` before sending packets over the network.

#### 3. X-Frame-Options
*   **Why it works:** Prevents **Clickjacking** (User-Interface Redressing). Attackers frame a target site inside a transparent `<iframe>` overlaid on top of a decoy game or button, tricking users into clicking buttons (e.g., "Transfer Funds") unknowingly.
*   **Directives:**
    *   `DENY`: Completely forbids any domain from loading the site in a frame.
    *   `SAMEORIGIN`: Allows framing only if the framing page shares the exact same origin.
*   **Example:**
    ```http
    X-Frame-Options: DENY
    ```

#### 4. X-Content-Type-Options
*   **Why it works:** Browsers historically tried to guess ("sniff") the MIME type of a file if the server header was incorrect. An attacker uploading an image (`avatar.jpg`) containing embedded HTML/JavaScript could execute code if the browser sniffed it as `text/html`.
*   **Directive:**
    ```http
    X-Content-Type-Options: nosniff
    ```
    Forces the browser to strictly honor the declared `Content-Type`.

#### 5. Cookie Security Flags
When establishing user sessions via the `Set-Cookie` header, three security flags are mandatory:
*   `HttpOnly`: Forbids JavaScript from reading `document.cookie`. Prevents stolen session tokens via XSS.
*   `Secure`: Ensures the cookie is only transmitted over encrypted TLS/HTTPS connections.
*   `SameSite=Strict|Lax`: Restricts cookie transmission on cross-site requests, mitigating **Cross-Site Request Forgery (CSRF)**.

### Security Headers Summary Reference

| Header Name | Protects Against | Recommended Value | Why It Is Crucial |
| :--- | :--- | :--- | :--- |
| **`Content-Security-Policy`** | Cross-Site Scripting (XSS), Data Infiltration | `default-src 'self';` | Whitelists approved executable sources. |
| **`Strict-Transport-Security`** | SSL Stripping, Downgrade Attacks | `max-age=31536000; includeSubDomains` | Disallows insecure plaintext HTTP transport. |
| **`X-Frame-Options`** | Clickjacking / UI Redressing | `DENY` or `SAMEORIGIN` | Restricts framing within foreign web contexts. |
| **`X-Content-Type-Options`** | MIME-confusion / Drive-by downloads | `nosniff` | Blocks browser file execution based on guessing. |
| **`Referrer-Policy`** | Sensitive token leaks in URLs | `strict-origin-when-cross-origin` | Strips internal paths from the `Referer` header. |

## 7. Hands-on Lab Methodology: Inspection & Enumeration

*(Note: All penetration-testing activities are performed exclusively within an authorized lab environment.)*

When conducting network and web infrastructure assessments, follow a rigorous scientific methodology that cleanly separates objective telemetry from analytical deduction.

### Investigation Framework: Testing Infrastructure & Headers

```text
[ FACT ]        What is objectively true about the environment?
   |
[ OBSERVATION ] What did our tools report during initial scans?
   |
[ HYPOTHESIS ]  What does this data suggest about the defenses in place?
   |
[ TEST ]        What targeted request or packet tests the hypothesis?
   |
[ RESULT ]      What did the target appliance return?
   |
[ CONCLUSION ]  What confirmed finding can we conclude?
```

### Lab Walkthrough: Analyzing a Perimeter Target

#### Step 1: Initial Discovery & Inspection
*   **Fact:** The target lab host is reachable at IP `10.10.110.45` with standard web ports open.
*   **Observation:** We run `curl -I` against the target to retrieve HTTP response headers:
    ```bash
    curl -I https://10.10.110.45/login
    ```
    *Observed Output:*
    ```http
    HTTP/1.1 200 OK
    Date: Mon, 31 Aug 2026 10:15:22 GMT
    Server: Apache/2.2.8 (Ubuntu) DAV/2
    Set-Cookie: PHPSESSID=39bf829a1c; path=/
    Content-Type: text/html; charset=UTF-8
    ```
*   **Hypothesis:**
    1.  The application completely lacks critical security headers (`Content-Security-Policy`, `X-Frame-Options`, `Strict-Transport-Security`).
    2.  The cookie lacks `HttpOnly` and `Secure` flags, leaving sessions vulnerable to theft.
    3.  The banner reports `Apache/2.2.8`, which was released in 2008. An ancient version exposed alongside modern web services might indicate a **low-interaction honeypot** decoy.

#### Step 2: Probing Defenses & Distinguishing Real Services from Decoys
*   **Test A (Testing for Clickjacking Vulnerability):**
    Create a local proof-of-concept HTML file loading the target in an `<iframe>`:
    ```html
    <iframe src="https://10.10.110.45/login" width="500" height="500"></iframe>
    ```
    *Result:* The page renders cleanly inside the iframe without being blocked by the browser.  
    *Conclusion:* **Vulnerability confirmed.** The application is vulnerable to Clickjacking due to the missing `X-Frame-Options` / `frame-ancestors` directive.

*   **Test B (Testing for WAF Filtering):**
    Submit a known SQL injection test vector via `curl`:
    ```bash
    curl -s -o /dev/null -w "%{http_code}\n" -X POST "https://10.10.110.45/login" \
         -d "username=admin' OR '1'='1&password=password"
    ```
    *Result:* The server immediately responds with `403 Forbidden` and a custom response header `X-CDN-WAF: Blocked-Request`.  
    *Conclusion:* An active **Web Application Firewall (WAF)** is inspecting POST request bodies. Basic unencoded SQLi vectors are intercepted before reaching the backend web server.

*   **Test C (Testing the Suspected Honeypot Port):**
    The port scan also reported open port 2222 (SSH). We connect and test basic interactions:
    ```bash
    ssh -p 2222 root@10.10.110.45
    ```
    *Result:* The service accepts any password (e.g., `root:root`). However, running common bash commands (`cat /proc/version`, `ls -la /root`) returns either generic hardcoded outputs or immediate session resets. Outbound ICMP/DNS requests from the shell fail completely.  
    *Conclusion:* Port 2222 is an emulated **low-interaction honeypot (such as Cowrie)** intended to trap automated brute-force scripts. It is not an authentic administration shell.

## 9. How It All Works Together: Attack vs. Defense Scenarios

To solidify how these moving parts interact in a production infrastructure, let us trace two opposing scenarios through the defense-in-depth pipeline.

```text
SCENARIO A: LEGITIMATE ENTERPRISE USER
[User Browser]
      |
```
