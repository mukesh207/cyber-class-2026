# Path Traversal, Broken Access Control & Broken Authentication

> **Course:** Cybersecurity
> **Date:** 2026-09-02 | **Session:** 10

---

## 1. What is it?
This session covers key OWASP Top 10 vulnerabilities related to unauthorized access, along with data manipulation techniques:
- **Path Traversal (Directory Traversal)**: An attack that allows reading files outside the restricted web server directory (e.g., `/etc/passwd`).
- **Broken Access Control (BAC)**: When a user can perform actions or access data they aren't supposed to (e.g., a standard user accessing the admin dashboard).
- **Broken Authentication**: Flaws in how user identity and sessions are managed, allowing attackers to hijack accounts.
- **Encoding vs. Decoding**: The process of transforming data into a new format (e.g., Base64, URL Encoding) for safe transport across systems. **Not to be confused with encryption or hashing.**

## 2. Why does it happen?
- **Path Traversal**: Developers take user input (like a filename) and use it directly in a filesystem API without stripping out navigation characters like `../`.
- **Broken Access Control**: The server trusts the client too much. Security checks are only hidden in the UI (e.g., hiding the "Admin" button) instead of being validated on the backend.
- **Broken Authentication**: Usually caused by poor session management—such as predictable session cookies, failing to invalidate sessions after logout, or transmitting credentials in plaintext.

## 3. How does it work?

**Path Traversal Mechanism**
```text
Intended access: http://site.com/get_image.php?file=cat.png
Server looks in: /var/www/html/images/cat.png

Malicious access: http://site.com/get_image.php?file=../../../../etc/passwd
Server resolves: /var/www/html/images/../../../../etc/passwd -> /etc/passwd
```

**Broken Access Control vs. Broken Auth**
- **Broken Auth:** "I can log in as you" or "I can steal your session."
- **Broken Access Control:** "I am logged in as me, but I can view your private data."

**Encoding Example (Base64)**
Base64 translates binary data into 64 printable characters so it can safely travel via HTTP.
`admin` -> Base64 Encoding -> `YWRtaW4=`

## 4. Where is it used / found?
- **Path Traversal**: Found in URL parameters handling files (`?page=`, `?file=`, `?doc=`), API endpoints fetching PDFs/images.
- **Broken Access Control**: Insecure Direct Object References (IDOR) in URLs (e.g., `?user_id=1001`).
- **Broken Authentication**: Login pages, password resets, session cookies, "Remember Me" tokens.
- **Encoding**: Everywhere in web traffic. URLs use URL Encoding (`%20` for space); JWT tokens and HTTP basic auth use Base64.

## 5. How do I identify it?
- **Path Traversal**: Fuzzing parameters with `../` and checking if system files like `win.ini` or `/etc/passwd` are returned.
- **Broken Access Control**: Log in as User A, capture the request, then replace User A's ID with User B's ID. If it succeeds, BAC exists.
- **Broken Authentication**: Check if session cookies change upon login/logout. Check if session tokens look easily guessable (like sequential numbers: `session=442`).

## 6. Hands-on / Lab Methodology

**PTG: SQL Injection Tasks**
- **What to test**: Form fields and URL parameters. Inject `UNION SELECT` statements to join your malicious query with the original query to extract data.
- **Expected result**: Database tables and user credentials printed on the screen.

**PTG: Broken Access Control**
- **What to test**: Attempt to access `/admin` endpoints with a standard user account. Change numeric IDs in API requests (`/api/profile/55` -> `/api/profile/56`).
- **How to test safely**: Use Burp Suite to intercept a valid request, modify the identifier, and forward it.
- **Expected result**: Accessing someone else's data or administrative functions.

**PTG: Broken Authentication**
- **What to test**: Session cookies. Check if the site uses predictable cookies. Decode the cookie if it looks like Base64.
- **How to test safely**: Base64 decode a cookie like `dXNlcj1hZG1pbg==`. If it reads `user=admin`, modify it to another user, re-encode, and inject it back into your browser.

## 7. Failed Attempts & Why
- **What was tried:** Finding a string that looks like `5d41402abc4b2a76b9719d911017c592` and trying to "decode" it using Base64.
- **Why it failed:** That string is an **MD5 Hash**, not encoded data. Hashing is a one-way mathematical function used for integrity/storage, whereas encoding is a two-way format transformation.
- **What that tells us:** You must correctly identify data formats. Hexadecimal strings are often hashes; strings ending in `=` are often Base64.
- **What to try next:** Use a tool like Hashcat or a site like CrackStation to crack the hash instead of trying to decode it.

## 8. Example
An attacker logs into an online banking app and notices their profile URL is `bank.com/account?id=405`. They change the URL to `bank.com/account?id=406` and suddenly see the financial details of another customer. This is a classic Broken Access Control vulnerability known as IDOR (Insecure Direct Object Reference).

## 9. Impact
- **Path Traversal**: Attackers can steal source code, configuration files containing database passwords, or critical system files.
- **Broken Access Control**: Total compromise of data confidentiality and integrity (attackers acting as admins).
- **Broken Auth**: Complete account takeover.

## 10. Detection
- **WAF**: Detects common traversal payloads (`../`, `%2e%2e%2f`).
- **SIEM/Logs**: Detects multiple failed login attempts (Brute force Auth) or standard users repeatedly requesting `/admin` URIs (BAC).

## 11. Prevention / Remediation
- **Path Traversal**: Never pass raw filenames from the user to the filesystem API. Use indirect references (e.g., User requests file ID `1`, server maps `1` to `secure_image.png`).
- **Broken Access Control**: Enforce authorization checks on the **server side** for every single request. Never rely on the client to enforce rules.
- **Broken Authentication**: Use strong, randomized, cryptographically secure session IDs. Implement timeouts and destroy sessions on the server upon logout.

## 13. Important Commands / Syntax
- `base64 -d` (Decode a base64 string in Linux: `echo "YWRtaW4=" | base64 -d`)
- `base64` (Encode a string: `echo -n "admin" | base64`)
- `%20`, `%27`, `%3D` (URL Encoded values for space, single quote, and equals sign respectively).

## 14. Interview Questions
- **Q: What is the difference between Encoding, Encryption, and Hashing?**
  Encoding is formatting data for transit (reversible, no key). Encryption scrambles data for confidentiality (reversible only with a key). Hashing creates a fixed-size signature for integrity (one-way, irreversible).
- **Q: Explain Insecure Direct Object Reference (IDOR).**
  It is a type of Broken Access Control where an application provides direct access to objects based on user-supplied input (like changing an ID in a URL), without checking if the user is authorized to view that object.
- **Q: How would you prevent a Path Traversal attack?**
  By validating input against a strict allowlist and using indirect object references (mapping user input to backend files securely) rather than appending user input directly to file paths.

## 16. Key Takeaways
- Broken Access Control is the most prevalent web vulnerability because it requires business-logic validation on every endpoint.
- Path Traversal abuses file I/O operations to read unintended system files.
- Broken Authentication results from weak session management, not just weak passwords.
- Encoding (like Base64 or URL encoding) provides zero security or confidentiality; it merely ensures safe data transport.
- Always perform Access Control checks on the backend server, never trust the client.

## 17. One-Minute Revision
**Path Traversal** lets attackers read server files by injecting `../`. **Broken Authentication** involves flawed login/session mechanisms, leading to hijacked accounts. **Broken Access Control** (like IDOR) occurs when users bypass permissions to access unauthorized data or admin endpoints. **Encoding** (Base64/URL) just formats data, unlike encryption which secures it. Prevention relies on strong, randomized sessions, server-side permission checks for *every* request, and never trusting user-supplied file paths.
